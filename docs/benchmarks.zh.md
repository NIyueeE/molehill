## 测量的是什么

一个**路径之下的工作负载**,从工具外部观测。每一个臂——产品在各种配置下的形
态、一个参照工具、或者路径上完全没有工具的对照——都被同样的探针驱过同样的工
作负载,走在同一条三 namespace 拓扑上,处在同一场战役的同一个阶段里:

- 一条**交互流**:每次 ping 新建一条 TCP 连接,声明 SLO 所用的那件仪器;
- **bulk TCP**:1 到 N 条流(iperf3),吞吐这条轴;
- **短连接**:新连接形成的 churn,即"抵达"的代价;
- **UDP**:一次限速的数据报会话,以及一段直到丢弃点的速率阶梯;
- 以及,对发布 sweep 而言,网络条件的一份**脚本化日程**,它在工具持续运行的同
  时原地切换,因此一个工具*如何适应*先劣化、后恢复的路径,本身就是测量的一部
  分,而不是藏在测量之前的预热成本。

一切都从外部观测(`/proc`、`ss`、各接口的计数器、各 namespace 的 TCP MIB、
iperf3 自己的接收端汇总),这正是同一个对端二进制、一份发布出去的配置与一个
对照臂都能被同一套仪器描述的原因——也正是任何工具的内部计数器从不出现在比较
里的原因。

测量是单机的:访客、服务端、客户端与后端同居一台主机,路径条件施加在拓扑的一
条 veth 腿上。因此绝对吞吐描述的是*这*台主机;能迁移到别处的是形状、排序与
SLO 行为。这条拓扑存在的意义,是让一个 L4 臂(终结 TCP)、一个 L3 臂(整个包
走 TUN)与对照臂都在**同一条路径**上被测:它们只在访客拨向的地址、以及写进各
自配置的模式上不同,再无其它。

交互流的 p99 在 **50 ms** 以内、错误率不高于 **0.5%**,这就是 SLO:它是容量斜
坡的中止条件、每张图里的虚线,也是 gate 在 clean 阶段检查的东西。劣化阶段*本
应*远高于它——那正是测量本身,而不是失败。

## bench 模型(测量标准)

`bench/src/bench/` 是标准,也是唯一的 runner。发布所公布的 sweep 不是第
二套仪器:它就是本模型的 `sweep` profile——产品与各参照工具上的 `timeline` 与
`capacity` 场景——这正是阶段日程与负载斜坡装在同一份结果文件里、同一份 schema
之下、同一道门禁之后的原因。

```bash
sudo -n just bench                     # the smoke profile, about a minute
sudo -n just bench --profile dev --aa  # the default loop for an optimization
sudo -n just bench doctor              # what this host can and cannot measure
just bench list                        # every metric, condition and profile
just bench report ~/tmp/bench-*.json   # a stored run: tables, floors, verdicts
just bench plot ~/tmp/bench-*.json     # its charts and markdown tables
just bench gate RESULTS.json           # may this run be published?
just bench-selfcheck                   # the model's own checks (a fast gate)
```

> **这两个系统调用指标是设备 I/O 读数,只有 L3 臂能产出。**
> `/proc/<pid>/io` 记的是文件与管道流量,不记 socket 载荷:在本容器内实测,200 MB
> 经过 socketpair 只让 `rchar` 增加 105 KB,而同样字节经过管道会让它增加 209 MB。
> 转发臂的字节从不跨越这条边界,读数描述的就会是运行时的管道而不是那条路径——
> 模型对这类臂记录**类型化缺失**,而 `just bench-selfcheck` 会在规则与指标列表
> 不一致时失败。对 L3 臂而言,这个读数正是它声称的东西:从 TUN 设备读出与写入
> TUN 设备的包。

### 模型强制的规则

- **臂必须写明它测的宽度;数据面的形态根本不是臂的参数。** 转发臂的 `pool_cap`
  是池的 `[client.data].tunnels`,L3 臂的则是透明认领的**车道预算**——
  一条车道一条连接,因为认领永不multiplex。数据面的 **carrier 同样不是臂的一维**:
  carrier 由产品在运行时决定(先试 mhd,建立不起来回退 TCP),既没有配置键可写,
  也没有臂字段可设。对照关系落在**路径**上——`--condition udp_blocked
  --condition-leg tunnel` 在 carrier 穿过的那条腿上丢弃 UDP,mhd 因此建立不起来,
  这一次运行量的就是回退路径(证据是回退那行日志与池输出里的 `carrier="tcp"`),
  而干净路径上的运行走的就是 mhd。如果目的是把某个 carrier 单独隔离出来测量
  (例如丢包条件下的纯 mhd 运行),就在启动 bench 的环境里设
  `MOLEHILL_DATA_CARRIER=mhd`:运行会把继承到的 `MOLEHILL_*` 开关记进
  instrumentation,所以这种强制是可审计的。形态本身由
  服务类型推导(转发服务多路复用,认领永不),所以仍写着 `mode` 的臂会被
  `just bench-selfcheck` 拒绝。下文的记录沿用各次运行当时目录里的臂名:记录里写
  `l3-mux`(池上一条流)、`l3-mux4`(四条流)或 `l3-raw4`(四条连接)的地方,现在的
  目录是 `l3`(产品默认,每条认领一条车道)与 `l3-budget10`(各认领共享的 carrier 预算
  ——L3 拓扑有五条认领,于是十条车道起始为每条两条,分配器会把空闲的那些集中到正在承
  载流量的认领上);而 `l4-mux1` 已删除,因为拓扑里
  UDP 的下限会拒绝只有一条隧道的池——"两条隧道池上的单条流"对应单流场景下的
  `l4-mux2`(见 [HANDOFF.md](../HANDOFF.md)「The mux×1 gap, measured before
  touching it」)。

- **一个指标只在代码里定义一次。** 单位、方向、它作为比值时所用的分母、能够
  产出它的工作负载种类,以及值得称为一个 claim 的最小差异,全都写在
  `model.METRICS` 里;下面那张表就是从这个注册表生成的,`just bench list` 会
  把它打印出来。一个指标若描述成一种算法、计算的却是另一种,
  `just bench-selfcheck` 会失败。
- **对照臂是强制的。** 每个场景还会在同一条拓扑、同一组端口与同一个后端上再
  跑一遍,路径上没有工具。没有它,慢探针和慢隧道就是同一个读数,所以本模型总
  是把一个工具臂*对着它自己的对照*上报,而不是单独上报。
- **一轮运行在取第一个样本之前,就陈述它的整套方法。** 结果文件带一个指纹,覆
  盖拓扑、各条件与时间线、各个场景及其*解析后*的参数、各仪器的节奏与本模型自
  身的代码。只有指纹一致时,两份文件才可以比较,而 `just bench compare` 会逐
  一列出每一个有差异的键,而不是印出两种方法之间的一个差值。
- **本轮运行测量它自己的分辨率。** 有一个臂会在两个名字下各测一次(`--aa`;
  在 `dev`、`full` 与 `stage` 里默认开启),这两半之间逐轮配对的差异就是本轮
  运行能够相信的最小差异。每个判定都会把该指标自身的显著性下限抬到那个数字,
  而本轮运行会把各道下限印在表格旁边——并且在判定列表之下,为每个本轮
  *分不出来*的格子印出一行规划:多少轮能到达该指标的下限,或者这个格子噪
  声大到加轮次也没用。16% 的分辨率是对本轮运行的一句陈述,不是一个借口:它
  现在自带一个可以直接行动的数字。
- **一个 claim 要预先注册、要过检验、要过区间。** 三条腿,每条都印在判定行
  里,而不是藏起来:
  - *显著性*——中位数差越过该指标的下限与本轮运行自身的下限,与以前一样;
  - *一致性*——配对轮次过一个**精确符号检验**,显著水平取本轮轮次诚实能
    支持的那个:三轮时是 `p = 0.25`,判定行把 `p` 和 `alpha_eff` 并排印出,
    于是短轮次的 claim 被明确标成一句 25% 错误率的陈述,而不是默默冒充
    5% 的证据(六轮可达 p ≤ 0.05;n 轮能给出的最小 p 是 `2/2^n`);
  - *区间*——对配对差的一个 **bootstrap 置信区间**(可复现:种子来自本轮
    的指纹)说明效应是*整体越过*阈值(claim 的形状)、*整体落在*阈值之内
    (有边界地证明没有值得叫的差异),还是*横跨*它(只是一个方向,如此而已)。
- **只有预先注册的终点可以 claim。** 默认是每个场景的 headline 指标;
  `--primary metric=…,scenario=…[,arm=…][,cell=…]` 在*开跑之前*声明更多(或更
  窄)的终点,而且这份声明进指纹——看完数字再挑赢家,改的是文件的身份证,
  而不只是它的故事。其余每一项比较都是**探索性的**:带数字上报,绝不成
  claim。主终点的 p 值过 Benjamini-Hochberg 校正,claim 还必须活过它。
- **一个判定有五种状态,而"没有 claim"如今占三种。** `claim`;
  `directional`(区间横跨它,或设计确认不了的方向);`indistinguishable`——
  如今它指两件*被言明*的事情之一:区间**落在**阈值之内(有边界地证明差异
  不值得叫),或者**横跨**它(分辨率不够,行里写明是哪一种);
  `single-round` 拒绝从一次测量里读出方向;`unavailable` 指明什么没有被测
  量。任何单个配对轮次被剔除就会翻盘的判定,在行里标 **FRAGILE**——只上
  报,绝不悄悄修补。丢掉超过一半轮次的格子被直接拒绝(`drowned`),判定和
  门禁都拒。
- **指纹里多了两把方法钥匙。** `primary`(上面的预注册终点)与
  `normalize`——`--normalize control` 把每个工具臂的逐轮读数除以对照臂
  *同一轮*的读数,在格子受宿主机限制的地方抵消宿主机的逐轮漂移;而在工具
  本身就是瓶颈的格子上,它会把本不存在的"不变性"制造出来,所以它是一项被
  言明的设计选择,不是默认值。iperf3 的版本号记录在仪器节奏旁边:一个版本
  可能改变模型读取的汇总字段,边界另一侧的数字与这一侧不可比。
- **证据跟着数字走。** 每个格子都记录它跑过的命令、它读过的计数器、探针拨向
  的端点、后端看到过的对端、逐轮的原始样本数组,以及它的探针留下的日志。分阶段
  的格子还带着它**在窗口内的形状**——交互流逐秒的中位数、p99 与失败次数,它自己
  两次尝试之间的间隔(比节奏更慢的探针,报出的是探针的负载,不是路径的),窗口
  自身两端的 unix 时间,以及这一阶段要求的 churn 速率与它实际达到的那个。九十秒
  的中位数,对一个平坦的阶段和一个"先快后慢"的阶段是同一个数,而这个差别正是
  首阶段的全部内容。结果文件随运行边跑边写,所以一场被打断的战役仍然可以分析。
- **结果住在仓库之外**,除非这一轮*就是*发布 sweep:一轮运行写
  `~/tmp/bench-<stamp>.json`,产物就在它旁边(发起运行的用户的家目录,即便在
  `sudo` 之下也是如此);`--out`/`--work` 可以把它们搬走,而一个已存在的
  `--out` 会被拒绝,除非给出 `--force`。

### 指标

由 `model.METRICS` 生成;`just bench list` 打印的是同一份注册表,而报告和判定
渲染出来的就是这些定义。
| 指标 | 单位 | 方向 | 是什么 | 除以 |
|---|---|---|---|---|
| `throughput_gbps` | Gbit/s | 越高越好 | 接收端窗口内的有效载荷字节数 × 8 / 测量窗口 | 工作负载的测量窗口 |
| `offered_gbps` | Gbit/s | 背景,不是判定 | 访客链路出方向字节数 × 8 / 测量窗口 | 工作负载的测量窗口 |
| `rtt_worst_1s_ms` | ms | 越低越好 | 交互流往返时间里最差的一秒均值:一次会被整段百分位抹平的突发 | 交互流的一秒 |
| `rtt_error_rate_pct` | % | 越低越好 | 失败的交互 ping 数 / (成功 + 失败) | 一次交互 ping |
| `churn_per_s` | 1/s | 越高越好 | 每秒建立的短连接数 | 该阶段的测量窗口 |
| `drift_rss_mib_per_min` | MiB/min | 越低越好 | 该臂 RSS 合计值在整轮运行上的最小二乘斜率:泄漏是随时间的斜率,不是一个水位 | 一分钟运行时间 |
| `drift_fds_per_min` | count/min | 越低越好 | 该臂打开的 fd 数的最小二乘斜率 | 一分钟运行时间 |
| `drift_threads_per_min` | count/min | 越低越好 | 该臂线程数的最小二乘斜率 | 一分钟运行时间 |
| `wedge_count` | count | 越低越好 | 探针发问却什么都没听到、持续超过 10 s 的区间数:一个在劣化下停止应答的工具,平均值是看不出来的 | 一次静默 |
| `wedge_max_s` | s | 越低越好 | 整轮运行中最长的一次这样的区间 | 一次静默 |
| `capacity_streams` | count | 越高越好 | 容量斜坡上,交互流仍满足 SLO 的最高 bulk 流档位 | 一条 bulk 流 |
| `capacity_headroom_pct` | % | 越高越好 | 1 - 可持续的最大流数 / 斜坡的上限 | 斜坡的上限 |
| `startup_s` | s | 越低越好 | 从进程启动到服务能应答一条新连接的时间中位数:访客在重启之后付出的代价 | 一次冷启动 |
| `startup_max_s` | s | 越低越好 | 本轮运行看到的最差一次冷启动 | 一次冷启动 |
| `slo_broken` | bool | 背景,不是判定 | 该格打破 SLO 时为 1(p99 高于 50 ms 或错误率高于 0.5%),于是一个档位的判定与它的数字一起走 | 一个被测档位或阶段 |
| `rate_per_s` | 1/s | 越高越好 | 完成的请求/响应对数 / 测量窗口 | 工作负载的测量窗口 |
| `rtt_p50_ms` | ms | 越低越好 | 探针逐次请求往返时间的 nearest-rank 中位数 | 一个请求/响应对 |
| `rtt_p99_ms` | ms | 越低越好 | 探针往返时间的 nearest-rank 第 99 百分位数 | 一个请求/响应对 |
| `rtt_max_ms` | ms | 越低越好 | 探针观测到的最差单次往返时间 | 一个请求/响应对 |
| `rtt_samples` | count | 背景,不是判定 | 取百分位数所依据的往返次数 | 无(样本数) |
| `udp_recv_mbit` | Mbit/s | 越高越好 | 探针收到的数据报数 × 载荷 / 探针自己的测量窗口(对一次 blast 来说,该窗口包含 drain) | 探针的接收窗口 |
| `udp_loss_pct` | % | 越低越好 | (发出的数据报 - 收到的数据报) / 发出的数据报 | 探针发出的数据报 |
| `udp_gap_p99_ms` | ms | 越低越好 | 探针收到的各次应答之间间隔的第 99 百分位数 | 一个收到的数据报 |
| `transport_open_p99_us` | us | 越低越好 | fresh 流开流时间的 p99：工具臂上是 mhd 流，control 臂上是 TCP connect。reuse 格子报为缺失而不是 0 | 一次开流 |
| `transport_first_byte_p99_us` | us | 越低越好 | 从写出请求到收到首字节的 p99：carrier 自己的往返，其上没有任何代理 | 一个请求 |
| `transport_recovery_p99_us` | us | 越低越好 | `max(0, complete_us - first_us)` 的 p99：**首字节之后**的等待，被修复或停滞的流在这里显形。不是整个往返 | 一个请求 |
| `transport_stream_error_rate_pct` | % | 越低越好 | 失败 attempt /（成功 + 失败），由 harness 自己计数 | 一个请求 |
| `udp_rtt_p99_ms` | ms | 越低越好 | 探针数据报 echo 往返时间的第 99 百分位数 | 一个被 echo 的数据报 |
| `setup_p50_ms` | ms | 越低越好 | 建立一条连接所需时间的中位数,前提是工作负载每次请求都新开一条连接。它只测访客到服务端的握手:服务端在接受之后才把访客与通道配对,所以隧道侧的抵达代价要看 `rtt_*`,不在这里 | 一条连接 |
| `cpu_s_per_gbit` | s/Gbit | 越低越好 | 工具 CPU 秒数(user+sys,两个 daemon 合计) / 访客报价的 Gbit | 访客链路出方向上的 Gbit |
| `cpu_cores` | cores | 越低越好 | 工具 CPU 秒数 / 测量窗口 | 工作负载的测量窗口 |
| `bytes_per_syscall` | B | 越高越好 | 每次设备 I/O 的字节数:工具进程的 rchar+wchar / syscr+syscw。**仅 L3 臂**——见表格下方的说明 | 一次 read/write 族系统调用 |
| `syscalls_per_s` | 1/s | 越低越好 | 每秒设备 I/O 调用数:工具进程的 syscr+syscw 除以测量窗口。**仅 L3 臂** | 工作负载的测量窗口 |
| `wire_per_visitor_byte` | ratio | 越低越好 | 隧道链路字节数(双向) / 访客链路出方向字节数 | 访客报价的字节数 |
| `mean_carried_packet_b` | B | 背景,不是判定 | 隧道链路字节数 / 隧道链路包数,双向 | 隧道链路上的一个包 |
| `rss_peak_mib` | MiB | 越低越好 | 在工作负载进行中采样,工具各 daemon 的 RSS 峰值之和 | 一组进程 |
| `fds_peak` | count | 越低越好 | 工具各 daemon 打开的 fd 峰值之和 | 一组进程 |
| `threads_peak` | count | 越低越好 | 工具各 daemon 的线程数峰值之和 | 一组进程 |
| `service_sockets_peak` | count | 越低越好 | 服务端自己的 namespace 里,暴露服务端口上的 socket 峰值:该架构为每个访客保留的状态 | 一个访客 |
| `transport_loss_detect_us` | us | 越低越好 | 从「更晚的包证明某段缺失」到「该段被重发」之间的等待，测在只有三包在飞的流上:投递延迟型丢包检测会缩短的就是这个数 | 一个被丢弃的范围 |
| `retrans_segments` | count | 越低越好 | 访客 namespace 与服务端 namespace 重传的 TCP 段数 | 一个 TCP 段 |
| `dropped_packets` | count | 越低越好 | 窗口内本拓扑各接口与 qdisc 丢弃的包数 | 一个包 |
| `mhd_lane_dup_pct` | % | 越低越好 | **最忙**那条载体 lane 所发出的 stream 字节里,「已经发过一次的范围」占的比例,读自 daemon 的逐 lane 窗口行。取最忙而非平均:载体通常只在一两条 lane 上这样,其余看起来健康。只有设了 `MOLEHILL_MHD_STATS=1` 且 `RUST_LOG=molehill=debug` 的运行才产出它;其它运行报告的是**带原因的缺失**,绝不是 0 | 一条 lane 发出的 stream 字节 |


有两条约定这张表说不出来,因为它们属于工作负载:

- **格子每秒 carried 不到 1 Mbit 时,比值不报。** 停滞格子的分母就是停滞本身,所
  以 `cpu_s_per_gbit` 与 `wire_per_visitor_byte` 在那里是缺失(表里显示为破折号),
  而 `offered_gbps` 照常报访客真正发出了多少——读者因此看得出「格子停了」,而不
  是「工具很便宜」。没有这道地板时,同一次运行里出现过 3 762 s/Gbit 与 436 wire
  bytes/visitor byte,而对应的格子 carried 不到半个 Mbit。
- **速率的窗口是仪器自己的,而且它是有名字的。** bulk 速率取接收端预热之后的
  窗口(iperf3 的);往返速率取探针的测量窗口,而不是解释器启动的那一刻(启
  动成本记录在 `meta.probe_startup_s` 里);数据报速率取探针的接收窗口,对一
  次 blast 来说它包含 drain。由计数器导出的比值(`cpu_s_per_gbit`、
  `wire_per_visitor_byte`、`syscalls_per_s`)用计数器的窗口,这个窗口恰好只框
  住工作负载的进程——所以一个比值的分子与分母覆盖的是同样的那几秒。
- **`wire_per_visitor_byte` 对单向流量有 1 的下限,对严格的请求/响应工作负载
  有 2 的下限**,因为它统计隧道链路的两个方向,而一次往返会在那里被搬运两次。
  要读它,就对着对照臂自己的读数读,绝不要对着 1 读。

### 场景

| 场景 | 工作负载 | 它支撑的 claim | 头号指标 |

| `bulk-n` | `bulk` | N 条流是聚合起来,还是共享同一个上限 | `throughput_gbps` |

| `transport-loss` | `transport_loss` | carrier 有多晚才重发「已被更晚的包证明丢失」的那段字节：三包在飞、中间那个由 harness 在整形腿上自己跑的盒子丢掉。**诊断格**——没有 control 臂，因为不含 carrier 的路径没有丢包检测器——所以变更靠比较同一格子的两次运行来判 | `transport_loss_detect_us` |

一个格子的**地板是这次运行的属性,不是这个格子的属性**。`bulk-n` 在同一台主机、
同一对二进制、同样臂数下的四次运行,A/A 孪生的离散度分别是 5.4%、3.9%、14.9% 和
52% —— 而那个 52% 的运行恰恰是数字看起来像产品差异的那次(它的基线读 3.1–3.2
Gbit/s,平时是 11.5)。这几次之间格子本身没变:同样二十四条样本落在波动两侧。
所以一次 bulk 比较要引用**它自己那次运行里**孪生的地板(表里就是这么做的),地板
超过门槛的运行会被报成「无法回答」而不是一个小差异——模型会直接印出这句话
("the run resolves 27 % against a 10 % floor — about 28 rounds would reach it")。
「把传输拉长就能压低地板」这个假设被实测**否掉了**:四秒窗口下孪生是 5.4%,十八秒
窗口下是 14.9%,所以移动地板的不是窗口,格子保留原来的窗口。

### profile

一个 profile 就是一份附带了方法的时间预算:跑哪些场景、每个臂测多少轮,以及
各场景采用的规模。`dev` 是一次优化工作应该用的循环,`sweep` 是发布所公布的那
一个;`--scale` 会把每条阶段时间线的保持时长缩短或拉长,但不改变日程的*形状*,
而由于 scale 会落进指纹里,一次缩短的运行永远不会被误认成一次发布运行。

| profile | 测量轮数 | 每个臂的预算 | 用途 |
|---|---|---|---|
| `smoke` | 2(+1 预热) | ~45 s | 快循环:每一个头号指标,以秒计而不是以分钟计 |
| `dev` | 4(+1 预热) | ~150 s | 一次优化工作的默认档:每一个场景,以分钟计 |
| `full` | 6(+1 预热) | ~420 s | 发布级的 sweep:全部内容,需要多久就跑多久 |
| `stage` | 2(+1 预热) | ~150 s | 一个条件、整套工作负载:一个形状问题,以分钟计 |
| `soak` | 1(+0 预热) | ~1200 s | 漂移这条轴:一条轮换路径,长时间保持 |
| `screen` | 3(+1 预热) | ~240 s | 一次开发 A/B:一个条件,两个构建交错 |
| `sweep` | 1(+0 预热) | ~3000 s | 发布 sweep:阶段日程与负载斜坡 |
| `nobulk` | 2(+1 预热) | ~300 s | 去掉 bulk 主线的同一阶段性日程:诊断用,不是门禁 |
| `carrier` | 3(+0 预热) | ~240 s | 单一条件长时间保持、去掉 bulk 主线: L3 的 wedge 是不是载波本身 |

## 怎么读这些图
六张图,每张回答一个问题,每张只在这一轮真的带着那份数据时才画,并且每张都在
页脚里带着自己的方法:

- **时间线主图**——按臂给出交互流逐阶段的 p50(实线阶梯)与 p99(虚线),纵
  轴取对数,SLO 画成虚线,阶段条带加底纹(clean 与劣化相对),wedge 标出,
  它下面还有逐阶段的 bulk 吞吐。它回答"路径变化时会发生什么";
- **小倍数图**——每个阶段一个面板,每个臂一根棒棒糖(圆点 = p50,横杠 =
  p99,竖线 = 最差单次往返):散点盖掉的那个比较;
- **容量曲线**——吞吐与 p99 对报价负载,标出 SLO 线与每个臂的最大可持续档
  位:可持续负载就是曲线穿过那条线的地方;
- **UDP 阶梯**——接收速率与丢包对报价速率,并带上无丢包参照;
- **漂移面板**——整轮运行中的 RSS、打开的 fd 与线程数,并印出拟合出的每分钟
  斜率:泄漏是斜率,不是水位;
- **成本柱**——每个臂每承载 1 Gbit 所花的 CPU 秒,也就是 CPU 成本指标存在的
  意义。

没有携带任何读数的格子画成 `x`、印成 `- (reason)`,绝不印成 `0`:"路径什么
都没承载"与"没有人能测出它承载了什么"是两个不同的发现。

**要了 bulk 却一个字节都没承载的阶段是失败,不是一个快的阶段。** 它的延迟是一个
空路径的测量,所以 `streams > 0` 而承载字节**恰好为零**的格子是 `ok=False` 并带该
原因,gate 会把它当作"没有测到的一轮"拒绝,而不是去判定它那个(很漂亮的)延迟。
实测:一次 campaign 里六个末段格子有五个什么都没承载却报了通过——因为一个不再转发的
工具,会在它最空的那个阶段拿到整轮最好的数字。判据是**恰好为零,绝不是阈值**:速率档
本来就该读小值(`rate20` 在 20 Mbit/s 整形器下承载 19 Mbit/s),所以一次分阶段运行
里最小的诚实值就是整形器自己的速率,比零大好几个数量级。

### 怎么读一个格子

- **阶段的 bulk 格是整个窗口上的负载,并且标明是哪一侧测出来的。** 读数取发送侧
  在该阶段测量窗口内的字节数、按区间跨度加权——不是它最好的那一秒,因为 netem 会
  把一次突发送进它选中的任意区间,峰值因此是整形器日程的属性。决定哪一侧说话的是
  **测量本身,而不是档位**:当发送侧的记账失效时——客户端的 `end` 事件这么说,或该
  阶段有一半以上区间读数为零字节,也就是 socket 缓冲把整段负载吸了进去——读数取
  **接收侧自己的窗口**,图表与 README 用 `*` 标出;若连接收侧汇总也没有,该格**就是
  没有读数**,并写明原因,而不是拿失效的那一侧充数。某一格用了哪一侧与它一起记录
  (`bulk_gbps_source`),回退留给仍然需要它的格子(`jitter`)。
- **整形档的交互格是背景,不是判定。** 主导它的是 harness 自己装上的 netem 队列,
  而单轮并不重复:在本机上用同一套未改动方法跑三轮,整形档的 p99 格移动 5-24%
  (双腿作用范围下最高 48%),而 gate 对单阶段 p99 用的限值是 25%。因此 gate 对
  整形档只**上报**数值、只对暴涨(3 倍以上)判失败,而 README 把这些列标成背景,
  不在其中挑赢家。**队列深度按档位写明,它的丢弃也被记录**,所以"这一格是整形器
  主导的"是一个读数而不是一句托词:某个阶段的 qdisc 丢掉了递给它的流量、或一直
  顶在队列上限,那它测的就是整形器,它的交互数字与工具无关。
- **没有读数的阶段会说明原因。** 图表表格里的 `— (reason)` 与结果文件里的
  `bulk_gbps_source`,把"路径什么都没承载"与"没有人能测出它承载了什么"区分开;
  一个光秃秃的 `0` 做不到——那正是记账失效的发送侧对一条满载路径给出的数字。
- **每个阶段的数字都带着自己的样本数。** 一个阶段的 `rtt_p99` 是该阶段交互样本的
  nearest-rank 百分位,所以样本不足一百时,"p99" *就是*最差的那次观测——饱和运行
  中被整段楔住的阶段往往只有几十个样本,此时报的是最差单次测量而不是尾部估计。图表
  用 worst-second 刻度标出它;结果文件每阶段都带 `rtt_n`,读者因此能分辨一个格子是
  哪类数字。

## 条件与阶段日程

### 负载发生器自身的极限

访客端是一台在负载下的客户端,而客户端有它自己的极限,那不是工具的极限。其中一个
足以改变读数,值得写下来:churn 类场景**每个请求新开一条连接**,约每秒 2 900 条,
于是访客命名空间里会攒下约 174 000 个处于 `TIME_WAIT` 的 socket,而默认端口范围
只有 28 231 个。用尽之后探测器的 connect 被拒,它退避 50 ms,这些等待落在测量窗口
里——一轮本来每秒 2 900 次抵达的样本会变成每秒 183 次,而原始样本自己就写着:
`connect_errors=3773`(共 6 400 次尝试)。它对 A/A 孪生的影响和对被测臂一样大,
这正是它看起来像工具间歇性崩塌的原因。

所以拓扑**只在访客命名空间里**设两个开关:`net.ipv4.tcp_tw_reuse=1`(允许把
`TIME_WAIT` 的四元组复用于新的*出向*连接;内核默认值 2 只对回环生效,而访客是走
veth 拨号的)和 `net.ipv4.ip_local_port_range=1024 65535`。两者都是负载发生器
自身的卫生措施,都不改变被测的东西。作为第二道防线,一轮里若被拒的 connect 超过
二十分之一,该格会作为失败格报出、点名端口耗尽,而不是当吞吐数字报出——于是一个
饿死的轮次永远不会被读成慢工具,失败和计数都留在原始的逐样本产物里。

### 时间线

**分阶段场景**(`timeline`、`soak`、`cost`)走的是一条*时间线*:一串有序的
阶段,每个阶段是一种条件持续若干秒。某一轮用的是哪条时间线、以及施加在它各段
保持时间上的缩放,都记录在结果文件里。

- **`sweep`** 是发布日程:`clean` → `rtt100` → `loss1` → `loss5` → `rate100`
  → `rate20` → `jitter` → `clean`,并且首尾都是 `clean`——因为"路径恢复之后
  这个工具还是原来那个工具吗"本身就是问题的一部分;
- **`soak`** 用一条更短的日程轮转更长时间:`clean` → `loss1` → `rtt100` →
  `loss5` → `clean`;
- **`single`** 只有一个阶段——`cost`、`screen` 这类运行测的那个固定工作点。

`--scale` 会按比例缩放每一段的保持时间,而不改变顺序与集合,因此同一种形状既
能在两分钟内回答问题,也能跑四十分钟;缩放会写进指纹,因为用过它的那一轮测的
是另一种方法。

**分阶段格子的 p99 只来自一条 series,不是三者的和。** 一个阶段同时跑三个探针——
交互探针(每 50 ms 一条新建 TCP 连接、发一个 64 字节 echo)、churn 探针(每秒
十六条新建连接)与一个数据报探针——各自喂给不同的指标:`rtt_p99_ms` 只由交互
series 产生,`churn_per_s` 来自 churn series,`udp_rtt_p99_ms` 与 `udp_loss_pct`
来自数据报 series。它们是同一时刻对同一个网络的三次测量,**永远不会被合并成一个
百分位**;阶段结果里同时记下每条 series 产生了多少样本、以及实际启用了哪几条。

探针集合本身也是方法参数。`--series interactive` 只启那一个探针,
`--series interactive,churn` 启两个。取子集是**诊断**用途——"同一台机器上再跑
一个探针,会不会推动第一个探针的尾部"——绝不是发布配置:没有交互 series 的运行
根本拿不到分阶段的 `rtt_p99_ms`,而 gate 会拒绝一个它无法判定的 clean 阶段。

**单条件运行**(`--condition NAME`,用于其余所有场景)是同一套词汇去掉日程:
一个格子、一种条件、一个数字。

| 阶段 | 模拟什么 | 施加到路径上 | `sweep` 保持 |
|---|---|---|---|
| `clean` | 健康网络(对照) | 无 | 150 s |
| `rtt100` | 长途或卫星链路 | 100 ms 延迟、10000 包队列 | 120 s |
| `loss1` | 有丢包的 wifi 或移动链路 | 10 ms 延迟、1% 丢包、1000 包队列(这一档就是要尾丢弃) | 120 s |
| `loss5` | 严重拥塞的路径 | 100 ms 延迟、5% 丢包、10000 包队列 | 120 s |
| `rate100` | 100 Mbit 上行 | 100 Mbit/s、20 ms 延迟、2000 包队列 | 120 s |
| `rate1000` | 千兆城域链路：快到路径不该是 carrier 的极限，且 RTT 短到窗口天花板无法躲进长往返里 | 1 Gbit/s、2 ms 延迟、4000 包队列 | 仅定向格子 |
| `rate100_shallow` | 千兆以下 100 Mbit 上行、队列约 11 ms：浅到没有丢包响应的发送方会把它打满，于是丢的是发送方自己速率的包 | 100 Mbit/s、20 ms 延迟、100 包队列 | 仅定向格子 |

| `loss1_rate100` | 100 Mbit 且同时丢包的上行——选择载体时真正面对的有损 WAN | 100 Mbit/s、20 ms 延迟、1% 丢包 | 仅专注格 |
| `jitter` | 缓冲区膨胀的接入链路 | 20 ms 延迟 ± 10 ms、10000 包队列 | 120 s |
| `loss1_buf` | 有损路径,缓冲区大但有限:深到足以让尾丢弃不再是主因,又浅到不会把 RTT 抬起来(10000 包 ≈ 14.7 MB,545 Mbit/s 下约 27 ms 常驻排队) | 10 ms 延迟、1% 丢包、10000 包队列 | 仅专注格 |
| `loss1_deep` | 同样 1% 丢包,但队列足够深不会尾丢弃——用来把 carrier 的丢包恢复与整形器自身的丢弃区分开 | 10 ms 延迟、1% 丢包、100000 包队列 | 仅专注格 |
| `udp_throttled` | **限速**而非拒绝 UDP 的路径:依赖 UDP 的 carrier 仍能建立,但只能承载限速器放行的部分(10000 包/秒 ≈ 1472 字节数据报的 117 Mbit/s),而不走 UDP 的 carrier 不受影响 | 在腿上对 UDP 下 `iptables -m limit`(先放行后丢弃;只允许 `tunnel` 腿——放错腿会被拒绝) | 仅专注格 |
| `udp_blocked` | 丢弃 UDP 的路径:数据面的第一个 carrier 建立不起来,于是这次运行量的就是 **TCP 回退** | 在腿上对 UDP 下 `iptables -j DROP`(只允许 `tunnel` 腿——放错腿会被拒绝) | 仅专注格 |
| `clean` | 恢复——工具还是原来那个工具吗? | 无 | 150 s |

日程、时长、采样率与 SLO 都记录在每份结果文件里(`meta`),因此任何一张图总
能追溯回产出它的方法;每个档位施加的整形参数也在其中——包括每个档位的队列深度,
它决定整形器最多能压住多少流量,因而也决定了一次突发穿过它能造成什么。

**整形档的队列是写明的,不是 netem 的默认值。** 那个默认值是 1000 包,而且它并不
中性:一个 qdisc 在途要压住 `递交速率 x 延迟` 个包,所以在 `rtt100` 的 100 ms 下,
一条 37600 包/秒的流需要 3760 包的队列,而 1000 包的队列会**丢掉其中 73%**。这正是
透明 L3 那一行遇到的事——那条腿每秒送出 9400 包、丢掉 28180 包,而证据里所有设备
计数器全程读数为零,因为 `/proc/net/dev` 看不见 qdisc 的丢弃——这个丢包被当成工具
的性质读了整整一个周期。现在凡整形延迟的档位都带 10000 包(100 ms 下即 100000
包/秒),与 `loss1_buf` 当初为"尾丢弃不成为主因、又不留下常驻排队"定下的同一个值;
确实**想要**尾丢弃的档位自己写明更小的上限,`loss1` 就是这么做的。这个读数是可以
核对的而不是一句承诺:每个阶段的 qdisc 丢弃数与常驻 backlog 都与设备计数器一起
写进它的证据里。

### MTU 档位

另有两条路径档承载**分片**这一维,它们刻意不出现在任何默认日程里:

| 路径档 | 模拟什么 | 施加到路径上 |
|---|---|---|
| `mtu1280` | 隧道,或 IPv6 最小可容忍路径 | 接口 MTU 1280 |
| `loss1_mtu1280` | 既丢包又会分片的链路 | 10 ms 延迟、1% 丢包、接口 MTU 1280 |

MTU 是**接口**属性而非 qdisc:使用这两档的阶段会改变该阶段内 **`lo` 上每一个
包**的路径——包括对端的、harness 自己的、以及工具控制面的包。这也是它们不进
默认时间线、只作为专注格运行的原因(`--condition loss1_mtu1280`,或用
`--profile screen` 在同一格上 A/B 两个构建)。`meta.mtu_restore_to`
记录运行开始时接口的 MTU,harness 在收尾时恢复它,恢复失败会**报错**而不是沉
默——残留的 1280 会毒化该主机之后每一次运行。这一维存在的理由:`lo` 的 MTU 是
65536,没有它任何数据报都只占一个分片,"丢失一个分片的代价"根本无法测量。读这两
档时请与下面的 `carrier` 各行合看。

### 每个 stage 拥有自己的条件

timeline 的每个 stage **装上自己的条件,并在 stage 结束时——无论成功还是失败——把那条腿
恢复成 clean**。这不是整洁问题:一个中途死掉的 stage(工具不再应答、sink 没起来)过去会把它
装上的条件留在原地,于是之后的每一个 stage、每一个**臂**都在一条没人要求的路径上跑。这是
实测出来的,而且它让一整次五臂 sweep 作废——一个臂丢了 `loss5`,它自己四个 stage 跟着丢,
下一个臂丢了两个 stage 加全部八级容量,再往后的两个臂什么都扛不动,门禁于是报出 69 个失败,
而其中零流的恰恰是**参考工具**。

所以一个格缺失或读不出时,先和它前一个 stage 对照,再对工具下结论:一次连 peer 都失败的运行,
是关于这次运行的陈述。这就是 [AGENTS](../AGENTS.md) §10 那条「一个失败不能毒化下一个样本」
的规则,从进程推广到条件。

### 整形作用范围

**一个条件只施加在拓扑的一条腿上**:`--condition-leg visitor`(默认)整形访客
与服务端之间的链路,`--condition-leg tunnel` 整形工具载体所穿越的那条链路。选
定那条腿的两端都会被整形,因为 netem 只作用于出方向——只整形一端就只整形了一个
方向。因此每一次注入延迟只付一遍,付在访客这一侧——真实部署的 WAN 就在这里;
backend 腿(客户端进程到它转发的后端)不整形,因为后端就在工具旁边。某一轮实际
用的是哪条腿,随它的结果 meta 一起记录。

只有数据面被整形。工具的控制通道留在未整形的路径上:整形它会打死心跳,把一
次容量测量变成一场 wedge 研究。

**限速档的读数取自接收端。** 不加限制的发送侧会破坏自己的记账:它的写入会先灌
进一个远大于整形路径排水能力的 socket 缓冲,于是发送侧自己的区间读到零字节,而
路径仍在继续承载。本模型不去限制客户端的 socket 窗口;它为每一个速率引用
**接收端**的窗口(上面那张表的第一个约定),而接口计数器把路径真正搬运的量放在
它旁边。这就是为什么一个 `rate20` 格是一个读数,而不是客户端缓冲的一个属性。

### 阶段交接

上一个阶段彻底安静下来之前,下一个阶段不会开始。阶段边界会杀掉该阶段的 bulk
客户端,而被杀掉的 TCP socket 仍会把内核还握着的数据继续交付出去,也会带着自己
的 FIN 一直重传——用的还是当时挂着的那个 qdisc。此刻换整形,就是把上一阶段的收
尾排进下一阶段握手的同一个队列;又因为一个工具的数据面端口共享同一个 netem
class,一个被这堆收尾数据挤掉的 SYN 会让下一阶段开头的几秒报废。于是本模型在
**旧**条件下等待,直到路径按两个测量都算安静——排队不超过一帧
(`topology.DRAIN_TOLERANCE_B`,64 KiB)**且**没有任何处于"还能发包"状态的
socket(`ESTAB`、`FIN-WAIT-1`、`CLOSE-WAIT`、`SYN-SENT`、`SYN-RECV`)——两者都
连续两次轮询成立(`topology.DRAIN_QUIET_POLLS`),之后才施加下一阶段的条件。

两半都是容差。队列永远到不了零——交互、churn 与 UDP 探针和工具共用同一个
class,会永久在里面留下约 1.2 KB——所以一条"队列恰好为空"的规则只能靠耗尽预算
收场,那会让整个交接变成定时器驱动,起始状态取决于时钟而不是取决于路径。而"没
有 socket"也不能等于"没有非 LISTEN 的 socket":`FIN-WAIT-2`/`CLOSING` 会滞留
*数分钟*且不承载任何数据,而上面列出的那些状态恰恰就是会重传被杀 bulk 客户端内
核里那几十 MB 的状态。队列那一半是*读出来的*,不是假设出来的:`tc` 渲染
backlog 时带单位后缀(`b`、`Kb`、`Mb`、`Gb`),所以 drain 先把它解析成字节,再
作任何判断。

这次等待的预算(60 s)是**安全网,不是机制本身**:等待由判据结束,而一次被触发的
预算会被记录,而不是被吸收掉。这次等待花了多少、留下了什么,都随它前面的那个阶
段一起记录(`drain_s`、`drain_expired`、`drain_final_backlog`、
`drain_busy_sockets`),所以一个在繁忙状态下开始的阶段会自己说明这一点。

之后每个阶段都会拨自己的 bulk 脊柱,以该阶段的保持时长作为它的窗口,预热也按
它缩放(`-O` 取保持时长的四分之一,至多两秒)。某个阶段的 `iperf3` 客户端失败,
是那个格子的一次类型化失败,运行继续:一个坏掉的阶段毒不到下一个,而那个格子会
带着仪器自己给出的原因。

**属于仪器自身的失败会重测一次,而且只有这一类。**`iperf3` 的客户端在自己的控制
连接断开时会以 `control socket has closed unexpectedly` 退出,而它的 sink 随后会
报告「流已建立、整段零字节」——在汇总里,这和「载体转发了连接却不转发负载」完全
无法区分。在发布 sweep 上量过:丢了格子的那几个阶段里,发送端的窗口长到 13.5 MB、
flight 为 0,也就是说载体是**闲着**,不是坏着。

**某个阶段**以这个原因失败时,重新排空后当场再测一次;**某个场景的每一个**格子都以
这个原因失败时,重启之后再测一次——后者覆盖的是「一个场景就是一个格子」的那些场景。
两种情况样本里都带上 `retried_after` 记录第一次尝试的原因,门禁因此仍然看得见
「这个格子丢过一次」,而第二次仍然失败就照实算失败。其他任何原因都按原样报告,不做
第二次尝试。

## 怎么跑

```bash
# the fast loop, and the loop an optimization should use
sudo -n just bench
sudo -n just bench --profile dev --aa

# the release sweep: the staged schedule and the load ramp, five arms
just bench peers fetch
sudo -n just bench --profile sweep --out benches/records/results-bench-vX.Y.Z.json

# one condition, the whole workload (a shape question in minutes)
sudo -n just bench --profile stage --scenarios cost --arms molehill,frp

# an A/B: the same arm twice, two builds, interleaved, verdicts against the
# run's own noise floor
sudo -n just bench --profile screen --ab-arm molehill --binary-b /path/to/build

# an experiment with a knob the catalog does not carry: declare it
sudo -n just bench --arm id=l3-deep,txqueuelen=20000
```

`just bench doctor` 会在一轮运行不得不自己去发现之前,就把这台主机能测什么、不
能测什么说清楚(root、`/dev/net/tun`、iperf3、各对端二进制)。对端二进制来自
`just bench peers fetch`:取自 GitHub 最新 release 产物,绝不从源码构建,解析出的版
本记录在结果 meta 里。

## 怎么读一次结果

- **一个 profile 就是一种分辨率,而 smoke 的分辨率很宽。** 同一个未改动二进制在
  `smoke` 下反复运行(`--aa`),曾在往返格子上声称 13-20% 的差异、在最短的格子上
  声称 23-29% 的差异:在只有几秒长的臂上,模型自身的离散度就有这么大,而它会说
  出来,不会把它藏起来。请把 smoke 的 claim 当作一个假设,用 `dev` 重新测——
  `dev` 存在的意义正是如此。
- **格子表是带范围的中位数**,按臂在测量轮次上取。预热轮不计入;失败的轮次会
  被计数,并连同仪器的类型化原因一起列出,绝不混进平均值。
- **下限表就是本轮运行的分辨率**,按指标给出:A/A 差异、A/A 离散度、以及整轮运
  行中对照的漂移,再取三者中最大的那个,而一个 claim 必须越过它。产生最差读数
  的那个格子会被点名,因为那才是该多花时间的地方。
- **判定是按场景、按格子给出的**,每个工具臂对着对照给一份,再加上 A/A 孪生臂
  自己的判定——A/A 这一对声称有差异的那个指标,就是本轮运行分辨不了的指标,而
  它会明说这一点。
- **一份结果文件就是 `meta`、`samples` 与 `summary`。** `meta` 承载方法(指纹、
  解析后的场景参数、拓扑、各条件、各仪器的节奏、SLO)、来源(修订、二进制的
  sha256 与它自己那一行 `--version`、主机身份、两个校准探针、以及这次运行开始时的
  负载均值)以及臂列表;
  `samples` 是每个臂、每一轮、每个场景、每个格子一条记录,各自带着它的指标、
  它类型化的缺失与它的证据;`summary` 是分析从这些样本里推导出来的东西——而
  `just bench report` 会重算它,因为样本才是证据,`summary` 只是对证据的一次渲
  染。负载均值是**宿主机**的,不是容器的:在共享的 bench 主机上,它是唯一能说明这台
  机器当时是否适合被测量的字段——在人群底下取的那次运行应当被拒绝,而不是被比较。
- **`just bench plot` 从任意结果文件渲染出的正是本页描述的这些图**:时间线主图、
  小倍数图、容量曲线、UDP 阶梯、漂移面板与成本柱。
- **一个 CPU 数字可以拆成载体自己的各个相位。** 当这轮运行带着
  `MOLEHILL_MHD_STATS=1` 时,`just bench phases <工作目录或结果文件>` 会读取
  两个守护进程的累计日志,按每一个被计时的相位打印"每承载 Gbit 多少秒"和"每个
  事件多少纳秒":记录层的 seal 与 open、发送端的 run 组装与那次系统调用、接收端
  的每数据报路径,以及两个流句柄各付的那次拷贝。被采样的相位会按该轮真实的事件数
  放大回去,因为计时器每十六个数据报才量一个。它是**归因**,不是测量——放进结论的
  仍然是 `cpu_s_per_gbit`,它只回答那个数字去了哪里。

## 门禁

`just bench gate` 是一轮运行的数字在可以发布之前必须满足的东西。它会为每一个
问题报告它看到的结果,并让其中必须由人来处理的问题失败:

- **覆盖**——各场景声明过的每一个格子,每个臂都要有;
- **端点不变量**——没有任何 L4 臂或对端臂拨向它所转发的后端(透明臂是记录在案
  的例外:访客拨的是客户端拥有的那个地址,由客户端的内核把包送达);
- **clean 阶段上的 SLO**——针对产品自己的臂;某个参照对端没达到,会连它的数
  字一起上报,但绝不阻断一个 tag。一个**被测到、却没有往返样本**的 clean 阶段
  在这里**直接失败**:它被计入,于是它不可能成为一条绿色门禁悄悄跳过的格子;
- **漂移与 wedge 两条轴**——泄漏是随时间的斜率,wedge 是一次交互静默;wedge
  在任何长度的运行上都判定(一次静默不是斜率问题),而斜率只有在一轮运行长到
  足以承载它(十五分钟)时才判定,更短的运行其斜率只作为背景上报。**一次静默是
  "连续未获应答的尝试",从第一次的开始量到最后一次的结束,而不是样本之间的
  空隙**:交互探针是串行的,空隙其实是**下一次尝试自身的时长**,按空隙读会把一次
  "慢但成功"的应答当成 wedge——`loss5` 阶段里两次 5.1–5.5 s 的应答就被报成
  L4"静默了两次",而这是每个工具都要付的代价,因为有损路径上新建 TCP 连接的
  SYN 退避阶梯就是 1 s、然后 3 s。阈值取**两个尝试预算**(2 × 5 s)也是同一个
  理由:只等于一个预算时,一次未获应答的尝试按定义就是一次静默,这条轴就成了
  抛硬币;
- **容量斜坡**——工具**在哪一档**打破 SLO 才是那个测量值,所以斜坡的档位不由
  上面那条阶段 SLO 判定;判定的是**天花板**:产品自己的臂若停在声明的
  `streams_max` 之下就失败,因为一条在三档断掉的斜坡是容量回归,不是一个主机
  读数。参照对端的天花板只上报,不阻断;
- 以及带上 `--baseline` 时的**回归那一半**:与 `just bench compare` 所做的同一
  个比较,除非两份文件的方法记录一致,否则拒绝。

## 模型回答不了什么

写在这里,免得读者向一张图索要它从未测过的东西:

- **在仪器修好之前,churn 对比不能引用。** `churn-16` 每次请求都新建连接,而这个读数
  目前还不可信:2026-10-10 的三次运行中,所有退化格子都出在 L4 臂上(四轮完全没有样本、
  三轮 readiness 探针在整整 30 秒内连不上暴露端口),L3 臂一次都没有。这究竟是架构本身
  (每连接状态,或者一条访客连接在 L4 上多花的临时端口)、还是 harness 的问题(探针报零
  却不说为什么),正是这个场景能够给两种架构排序之前必须查清的事——探针必须先记录
  连接**为什么**失败,它的速率才值得引用。这一模式作为未决线索记在 HANDOFF.md,不是
  结论。

   *(2026-10-12 更新:原因已查明——见下文历史注记。探针现在会统计失败的连接
   (每个 churn 格子的 evidence 里有 `connect_errors`),新的运行可以区分"慢"与
   "端口耗尽";此修复之前测得的每一个 churn 数字仍不引用,上面那些退化格子是
   仪器伪影,不是架构结论。)*

- **加密要付多少，2026-11-08 之前无法回答。** 每个 L4 臂都写 `data_enable = true`，而**那正是转发服务的
  客户端默认**：未设置时解析为 `true`（`src/core/client.rs`），于是每条数据通道各自付一次 Noise 握手。
  另一个数据面——每条控制会话一次 Noise 握手、数据流一次都不付——是**透明 claim** 的默认
  （`[transparent.noise].data_enable` 默认 `false`）。所以本页的 L4 表格描述的是 L4 部署真正会跑的那个面，
  对 claim 的面不置一词。`l4-plain` 与 `l4` 只差这一个开关，所以这一对给加密（以及随之而来的开流形状）
  定价；目前还没有基于它的对比被发表。

- **对"大量小数据报"迟钝的接收端。** 每个 bulk 格子发的都是合并后的 run，一次
  `recvmsg` 就取回整段，所以"一次调用只取一个报文"的代价在其中永远不出现。而一次一个
  1 349 字节数据报的路径没有合并：2026-11-08 那种形状单向丢了 97%，而 `bulk-n` 在修复前
  后都读到 15.0 Gbit/s（throughput −0.4%，A/A 抖动 4.9%）——见
  [HANDOFF.md](../HANDOFF.md) §4.117。所以 bulk 格子给不了这类缺陷的定价，而一个按那种
  转发器形状写入的格子目前还不存在。

- **重排窗口（RACK）一类改动。** RACK 需要"更晚的包被确认"才能定锚，而没有任何格子把每条流的
  在飞包维持在 2–3 个：多流格子比三包阈值更深、阈值会先判损，单流格子丢的往往是 flight 里最后一个
  包、后面没有可锚的东西。两者在 2026-11-08 都测成零结果（见 [HANDOFF.md](../HANDOFF.md) §4.125），
  改动已回退；所以重排窗口的声明需要一个模型目前还没有的格子。

- **在本机上跑赢基于 TCP 的工具的 carrier。** clean loopback 格子上，mhd 的往返约 **45 µs，而裸 TCP
  socket 是 20 µs**；代理后的请求约 **113 µs，rathole 是 61**——因为 TCP 的 loopback 是内核到内核，而用户态
  数据报 carrier 需要一次内核不需要的任务跳，实测每方向 9.4 µs。去掉它要每连接一个 socket，已被裁定配置面
  变动过大。所以本页没有任何格子显示 mhd 领先 frp 或 rathole。carrier 买到的——不可靠数据报上的每流恢复、
  跨流无队头阻塞、可选 datagram 语义——**在这里没有任何场景测过**：丢包格子因整形器主导而并列，重排窗口格子
  不存在。见 [HANDOFF.md](../HANDOFF.md) §4.134 与 §4.145。

- **一次丢包究竟是随机的，还是 carrier 自己的速率造成的。** carrier 路径随机丢 5% 时，mhd 只承载同一格子干净时的
  约四分之一，而计数器说明了原因：窗口只长到 1.47 MB（天花板 16 MiB），在 200 ms 往返上就是 236 Mbit/s——
  正是实测的 290——而重传保持在 4.3%，恰好是丢包率。第一次丢包之后窗口每个窗口只加一个包，所以在长路径上恢复很慢。
  **这里没有任何格子让丢包率取决于发送速率**，因此无法判断「对丢包有反应的窗口」是有益还是有害：
  `loss1_rate100` 既有速率又有丢包，但它的队列足够深，丢的是整形器的包，不是发送方的。

- **来自另一台主机的数字。** 主机身份与两个校准探针随每一份文件一起走;在不同
  机器上的两轮运行会被拒绝,而同一台机器上、探针漂移超出容差的两轮运行也会被
  拒绝。
- **两个臂都贴在 loopback 上限上。** 在单机上,量程的顶端是路径本身,而不是工
  具,所以够到它的臂无法靠单轮运行分出先后:同一份未改动的代码三轮 sweep 下来,
  最快的两个臂读到 15.9-22.2 与 12.8-20.4 Gbit/s——摆动之大足以让两者的先后
  **反转**;而低一个数量级的一个参照工具变动不到 3%。把这两行读作对主机状态的
  一次读数,永远不要把它们的先后当成可以长期引用的结论。
- **每个条件只有一个样本。** 一个阶段格就是对该日程的一次遍历,所以单轮无法为
  它只访问一次的条件给出自身的重复性。日程会两次访问 `clean`(本轮自己的重复
  实验),其余由 A/A 这一对来测;比各道下限更小的差异,不是那一轮运行能分辨的。
- **劣化之下的控制面。** 被整形的只有数据那条腿:工具自己的控制通道留在未整形
  的路径上,因为整形它会把一次容量测量变成一次 wedge 研究。控制通道在丢包*之
  下*的任何行为,都在本模型射程之外。
- **工具自身的内部。** 被测量的一切都是外部可观测的,所以一个对端二进制与
  molehill 以完全相同的方式被测——两者的内部计数器都不会出现在比较里。可选的
  `MOLEHILL_*` 开关给一轮运行加上 molehill 专有的诊断;继承了任何一个开关的
  运行会把它记进结果 meta。
- **没有任何无工具路径能跑的东西。** 在对照臂上跑不了的场景,按声明就是
  `diagnostic`:它产出数字,从不产出判定。

## 每个配置选择的代价(逐项实测)

池自身的阈值——引擎 64 条流中达到 56 条时拒绝放置、修复死亡的隧道、5 分钟没有
任何字节流动就收割一次转发——是内部常量而不是设置项,并且只有在测量支持下才会
改变。池的宽度不在其中:它是 `tunnels`,其指导背后的实测就是下面的 `count` 行
(用固定池重新测量:干净 jumbo 路径、8 流下一条隧道 12.85 Gbit/s,八条隧道
22.81;`loss1` 上从一条隧道到两条 3.34 vs 5.92 Gbit/s)。

| 决策 | 选项 | 实测依据(退役的逐格模型) |
|---|---|---|
| `mode` | `"multiplex"`(默认) | 回环 1 流 10.0 Gbit/s,`direct` 为 19.2;8 流分别 19.5 vs 23.3;multiplex 吸收每连接的建连成本(churn ~4.8k 连接/s)并节省 FD / 端口 / NAT 映射 |
| `mode` | `"direct"` | 原始单流吞吐;每条流一条物理隧道(FD / 端口 / NAT 成本随流数增长) |
| `tunnels` | `1` | 所有流量共用一条隧道:没有聚合,所有流共享同一个重传域(回环 8 流聚合 9.2 Gbit/s,四条隧道时为 19.5;loss5 队头阻塞最大 2.5 s vs 1.6 s;而在固定池自己的格子里,8 流在 `loss1` 上读到 3.34 Gbit/s,两条隧道时为 5.92) |
| `tunnels` | `4`(默认) | 聚合越过单流(loss1 8 流 12.3 vs 4.5 Gbit/s)并隔离队头阻塞(rtt10 最大间隔 80.6,一条隧道时为 100.1 ms);yamux 上限 `count × 64` 条并发连接,计入放置自身的上限后为 `count × 56` |
| `tunnels` | `8+` | ~512 条并发连接(8 条隧道 × 每条 64 条 yamux 流);每服务 8 条物理隧道(NAT 映射 ×8),且在干净 jumbo 路径上 22.81 Gbit/s,一条隧道时为 12.85 |
| `carrier`(强制) | `mhd`(默认) | 在能过 UDP 的路径上产品自己会选的 carrier,也是 `cost` 指标所引的那个:同一格上 `cpu_s_per_gbit` 0.65 对 TCP 的 0.48。`MOLEHILL_DATA_CARRIER=mhd` 把它钉住,同时也让池的 carrier 规则失效 |
| `carrier`(强制) | `tcp` | UDP 被封锁或限速时的回退:需要回退本身的数字时用 `MOLEHILL_DATA_CARRIER=tcp` 钉住它,而不是用它来代表产生回退的那条路径 |
| transport | `"plain"` | 回环 10.0 / 19.5 Gbit/s(1 / 8 流) |
| transport | `"noise"` | 5.8 / 14.9 Gbit/s;RTT 代价亚毫秒;满载下 CPU 持平 |
| `pool_size` | 8 TCP / 2 UDP(默认值) | 16 路 churn 下建连到首字节 p99 ~3.5 ms;UDP 把不同访客分片到不同通道,绝不拆分单个会话(会话亲和) |
| 条带(striping) | 四条通道为一组(测量时用 `stripe_count = 4`;该键已移除——每组从一条开始,宽度不由别的访客的历史决定,见[内部设计](internals.md#data-channel-striping)) | 单条长连接不再被一条隧道流钉死:回环 1 流吞吐 +48.7%,代价是重排缓冲、RSS +8.7%、CPU +40.8%(每帧 CPU 减半,因为帧摊到了四个驱动任务上) |

### L3 数据面:瓶颈在哪(2026-10-10,本模型)

透明路径搬运的是**包**,而转发路径搬运的是字节:一条认领把每个 IP 包交给设备,
因此代价是"每包"而不是"每字节",模型要量的就是这件事的代价。下面四列来自同一台
主机、`--profile smoke --condition clean`、每臂两个测量轮,同一轮里带 A/A 孪生臂。
`bulk-1` 是穿过隧道的一条 TCP 流,`bulk-n` 是八条。

| 臂 | `bulk-1`,TUN MTU 1400 | `bulk-n`(8 流),1400 | `bulk-1`,TUN MTU 8000 | `bulk-n`(8 流),8000 |
|---|---|---|---|---|
| control(无工具) | 40.640 Gbit/s | 49.159 | 39.951 | 50.853 |
| `l3` | 4.335 Gbit/s | 3.934 | **8.000** | 5.772 |
| `l3~aa`(同一条臂测两遍) | 4.214 | 3.847 | 7.214 | 5.961 |
| `l4`(同一拓扑下的转发路径) | 8.991 | 22.333 | 7.996 | 22.629 |

有两点值得读出来:

* **L3 路径不随流数扩展。** 八条流比一条流搬得**更少**(3.9 对 4.3 Gbit/s),
  而转发路径几乎翻三倍(9.0 → 22.3)。上限是一条串行的逐包路径——一条认领就是
  一个设备读取任务加一个注入任务——而不是每条流的窗口,所以往一条认领里再开更多
  连接也抬不高它。
* **真正能动它的是包大小。** 把 TUN MTU 从 1400 提到 8000(链路 MTU 同步),同一条
  大流量从 4.335 提到 **8.000 Gbit/s**——1.84 倍——每 Gbit CPU 从 0.852 降到
  0.313 秒,只剩原来的三分之一。在这个包大小下,单条 L3 流在同一台主机上与转发
  路径打平(8.00 对 8.00),每字节 CPU 也只差 35 %(0.313 对 0.231)。

同样的效应也写在字节账上:1400 字节时,访客这条腿上有 7.5 % 的字节是隧道开销
(`wire_per_visitor_byte` 1.0755);8000 字节时是 1.5 %(1.0152),因为载体自己的
头部与确认从"每 1400 字节付一次"变成"每 8000 字节付一次"。

**后记(2026-10-16,offload 修复;2026-10-17、2026-10-18 重测):上面两条读法都已经过时。**
本节的二进制在 TUN 边界逐包分段;出厂的二进制声明了自己的分段 offload,接收的是
GSO 超级帧——见下文那条"撤回变更正"。这个修复的配对证据是单流的 smoke A/B:
2.0 → 3.4 Gbit/s。staged 运行的 L3 clean 格子承担不了与本节 4.335 的绝对值对比:
在本版本的几轮 sweep 之间,它在这台主机上变过三分之一以上(发布的一轮读
5.859 Gbit/s),而同一轮自己的两次 clean 读数相差不到 1%——这一格是这一行里
最不稳定的,它只支持"同一轮内的一对"。「不随流数扩展」与「包大小是杠杆」
两条都仍然成立——但设备内的包大小不再只由运维单方面设定,逐包串行的读取者也不
再是上限的全部。

**那么上限究竟是什么。** 同一拓扑,把 TUN MTU 设为 8000、链路 MTU 设为 9000,
并对转发路径的池加上不同上限——`l4-mux1` 就是"一条隧道",用它给单条载体连接定价:

| 臂 | `bulk-1`(1 流) | `bulk-n`(8 流) |
|---|---|---|
| control | 38.672 Gbit/s | 44.805 |
| `l3` | 7.136 | 5.847 |
| `l4`(池上限 4 条隧道) | 8.286 | 21.604 |
| `l4-mux1`(一条隧道) | 9.819 | 12.646 |
| `l4-mux8` | 9.058 | 21.955 |

在这台主机上,一条载体连接的上限就在 8–10 Gbit/s 附近——只有一条隧道的那个臂直接
说明了这一点,无论是一条流还是同一条隧道上的八条流——而转发路径之所以能超过它,靠
的是把流摊到**多条**隧道上。只由**一条**通道承载的认领因此按构造就停在这个"单连接
上限"上,这也解释了为什么它的 `bulk-n` 反而**低于** `bulk-1`:八条流穿过一条通道,
用的仍是同一条连接。

**正是首次引入认领成员集的那轮测量**终于抬动了上限。当时的模型把这两个键叫作
`members` / `[transparent.data].default_members`(默认 1——所以上面每一格的臂都保持原意);
当前模型把连接预算称为 `[transparent.data].tunnels`,把成员称为车道。四个成员、
内层流按规范化的五元组哈希分摊、巨型帧路径、每臂四轮实测并在同轮带 A/A 孪生臂:

| `bulk-n`(8 条流) | `l3`(直连,1) | `l3-mux`(多路,1) | `l3-mux4`(4 成员) | 孪生臂(同配置) | `l4`(转发池) |
|---|---|---|---|---|---|
| 吞吐 | 5.446 Gbit/s | 6.989 | **13.924** [11.528..15.091] | 13.598 | 29.166 |
| 每 Gbit CPU | 0.270 | 0.560 | 0.653 | 0.655 | 0.412 |
| FD | 39 | 69 | 69 | 69 | 99 |
| RSS | 18.35 MiB | 21.45 | 25.45 | 24.35 | 25.45 |

这条认领**接近翻倍**——13.924 对 6.989,孪生臂 13.598;而本轮自身的 A/A 下限是吞吐 3.34%、
孪生对之间 0.17%,所以这个增益高出噪声一个数量级。其余格子都守住:`bulk-1` 不可区分
(6.201 / 6.244 / 6.299)、`churn-16` **+22%**(6837/s 对 5586/s)、`rr-16` −1.8%(在孪生对
0.1% 的散布之内)、`fds_peak` 恒为 69(多路模式下成员是既有隧道上的 stream)、
`wire_per_visitor_byte` 不变,单成员认领的载体重传从 518 降到 **0**。

随它一起来的还有两个发现。分流在**逐成员**上可见:每一轮实测都把流摊到 4 个槽位中的 3 或
4 个,而且**两端对同一分布的读数相差不超过一个百分点**(服务端 23/52/24/0,客户端
23/53/24/0)——也就是说那把规范化 key 是在生产里被验证的,而不是只在单元测试里。另外,
这一片第一次跑出来的数字是 11.282/13.142,不是上表:FNV-1a 的低位很弱,八条 `iperf3` 流
之间变化的那个字节是临时端口,而那些端口**全是偶数**——于是取模读到一个塌缩的分布,把八条
流放进两个成员。这就是哈希末尾要接 splitmix64 终结器的原因,也是回归测试钉住那组实测
端口与每一种步长的原因。

这条包大小结论在运维侧的版本(连同配方)在[部署文档](deployment.zh.md#透明l3服务)。

**而在一条普通路径上——不用 jumbo 帧、也不用改 wire——杠杆是车道预算。** 天花板
是一条逐包串行的路径(每条认领一个设备读取者、一个注入者),所以认领的吞吐跟着它的
*车道数*走,而预算决定它能拿几条。同一主机、同一二进制、五条认领、八条内部流:一条
车道 2.351 Gbit/s、两条 3.283、四条 5.191。(量于 v0.11.0 之前的二进制——它
后来吃下的 offload 抬高了绝对值,上面的后记里有配对的 smoke A/B;车道这笔交易
本身没变。)它不是免费的——摊开繁忙认领那些流的车道,
同时也是压在「所有认领共享的那一个读取者」身上的压力,所以四条车道会花掉交互流的 SLO
余量(容量斜坡上只撑住三条流,而两条车道撑住八条)——这就是为什么出厂缺省值是两条,
四条是要主动去要的配置。一条车道的*代价*,以及想回到旧缺省值的部署的升级路径,归
[配置页](configuration.zh.md#透明l3服务)去讲;这一页负责的是测量本身。

本节末尾早先的一条读法已**撤回,且撤回本身是错的**(2026-10-16 的 offload 修复是它的
更正):TUN 上「每次系统调用能搬运多于一个包」的那条路(GSO/TSO)当时被否,理由是
1500 字节的路径拿不到它——TUN 不能把大于路径的包交给用户态——而且打开 TSO 要把校验和
与 GSO 状态逐包带上,那是改 wire。两半都不成立:内核交给读端的是 **GSO 超级帧**——一个
最大 64 KiB 的单元,自带 `gso_size`,对端据此重新分段——所以路径 MTU 根本不限制读的大小;
而那个状态本来就有 wire 形状(10 字节 virtio-net 头,整体中继,`NEEDS_CSUM` 原样随帧)。
路径缺的只是声明:`IFF_VNET_HDR` 加 `TUNSETOFFLOAD`。实测:同样 3.85 GB 的 bulk TCP,
无声明时以 576 071 次 1500 字节读抵达,有声明时以 59 160 次平均 65 212 字节的读抵达。
该修复已进入出厂二进制;探针在
[`bench/src/bench/utils/l3/tcp_tso_census.py`](../bench/src/bench/utils/l3/tcp_tso_census.py),
下文「剩下的是逐包系统调用成本」一段已按此改写。

### carrier 这一维现在是路径条件

产品在运行时自己选 carrier——先试 mhd,建立不起来回退 TCP——所以既没有构建要比,
也没有键要设。对照关系落在**条件**上:干净路径走 mhd,`--condition udp_blocked`
走 TCP 回退,同一个二进制在两条路径上各测一次就是比较本身。有两个开关用来隔离单个
carrier;两者都是诊断手段、都会作为 instrumentation 记录,都不是部署设置:

- `MOLEHILL_DATA_CARRIER=mhd` / `=tcp` 把整轮运行钉在一个 carrier 上。它同时让池
  自己的 carrier 规则失效——强制的 carrier 就是这次运行的答案,不是可以商量的偏好,
  池在它之下拒绝搬移任何隧道。
- `MOLEHILL_CARRIER_SWITCH_AT=<秒>` 让每个认领在这么多秒之后搬到另一个 carrier,
  这样"一次活的搬移要付多少"可以在决定要不要搬的策略写出来之前就被测到。

塑造过 TCP 对 KCP 那一维的数字,现在作为已发布的历史留在 `benches/records/` 里:
它们量的是一个本版本删掉的 carrier,那些 arm 已经无法构建,它们不是基线。今天用来
比较的,是每个场景打印的那张表——工具对它自己那次运行的对照臂。

### 一条新连接的抵达代价,按 carrier(2026-11-11)

两个 carrier 唯一拉得开的一维。测法是用 `MOLEHILL_DATA_CARRIER` 把每次运行钉在
一个 carrier 上,两次都是同一个二进制,跑 `dev` profile 的 `churn-16`(每次请求新开
连接,十六条并发,六轮,每轮带自己的 A/A 孪生)和 `rr-16`(十六条连接跨多个请求保持
打开):

| | `churn-16` `mhd` | `churn-16` TCP | `rr-16` `mhd` | `rr-16` TCP |
|---|---|---|---|---|
| 往返 p50 | 6.45 ms | 6.01 ms | 0.60 ms | 0.52 ms |
| 往返 p99 | **7.26 ms** | **6.66 ms** | **1.59 ms** | **1.34 ms** |
| 每秒完成数 | 2 427 | 2 607 | 23 900 | 27 745 |

也就是说:每个请求都要新连接时,两个 carrier 的尾部差**在 9% 以内**;连接被复用的那格
差**在 20% 以内**,速率分别差 9% 与 13%。抵达那格付的是一次流打开,而这次打开现在是
**密钥派生**而不是握手:车道的首条流跑 Noise KK,之后每条流用它派生出的密钥密封。
按产品自己的打开日志计,握手阶段是 **11 µs**,而 bulk 传输中的一次通道打开
中位 **211 µs**、p99 **9 ms**。

以上是跨运行的读数,每个文件自带 A/A 配对,所以只有两个文件的噪声地板能分辨的那一位
才谈得上方向。

### mhd 在哪里赢、在哪里输（2026-11-07）

carrier 这个问题有**按路径条件分的答案**，而不是一个 carrier。同一二进制、同一轮、
`--scenarios timeline`，每个 carrier 一个臂，用 `MOLEHILL_DATA_CARRIER` 各自钉住。

**除 `clean` 之外的每一行，条件都施加在 visitor 腿上**——carrier 并不走那条腿。所以那几行描述的是
*访客侧受损、carrier 路径干净*，而不是 carrier 在受损路径上的表现：

| cell | 条件是什么 | mhd p99 | TCP p99 | mhd Gbit/s | TCP Gbit/s | 判定 |
|---|---|---|---|---|---|---|
| `clean` | 不做任何塑形 | **59.0 ms** | **14.4 ms** | 8.61 | 8.50 | **TCP**，尾部差 4 倍 |
| `rtt100` | 加 100 ms 时延 | 403.2 | 410.1 | 2.57 | 2.51 | 持平 |
| `rate100` / `rate20` | 限速到某个速率 | 233.2 / 549.1 | 228.1 / 508.0 | 0.09 / 0.02 | 0.09 / 0.02 | 持平 |
| `loss1` | 1 % 丢包 | 1 061.1 | 1 052.1 | **4.79** | **6.07** | **TCP**，吞吐更好 |
| `jitter` | 20 ms ± 抖动 | **118.0** | **171.8** | 4.02 | **5.82** | 混合——mhd 的尾部、TCP 的吞吐 |
| `loss5` | 5 % 丢包 | **1 454.9** | **2 100.8** | **1.11** | **0.30** | **mhd**，两个轴都赢 |

**一句话读它。** 在那个形状里，一旦被塑形的那条腿丢得够多、把内核栈压垮，mhd 自己的恢复就胜过隧道里的
TCP carrier——5 % 丢包时它交出 **3.7 倍吞吐和紧 31 % 的尾部**；而在路径干净的每一处它都输，**尾部差 4 倍**，
因为新访客通道要付一次自己的 Noise 握手（中位 1 129 µs、最差秒 168 ms），而 TCP 隧道把这一步并进了
它本来就有的连接里。

**5 % 那个比值不能搬到 carrier 穿过的那条腿上。** 那一行塑形的是 visitor 腿，carrier 自己的路径当时是干净的，
所以它度量的是两层复合，而不是 carrier 在丢包路径上的行为。后来两次运行测的是 carrier 自己那条腿
（`--condition-leg tunnel`）：mhd 单独在那里读到 **0.074–0.174 Gbit/s**，而不塑形时是 1.19；**TCP carrier
在那条腿上一次都没跑过**——所以在两个 carrier 共用的那条路径上，它们之间没有任何比值。要得到那个比值，
就是把同一格子跑两次、用 `MOLEHILL_DATA_CARRIER` 各钉一个臂，上表每一行都是这样测出来的。

所以给运维的诚实说法不是"某个 carrier 更好"，而是：**哪个 carrier 更快是路径的性质，而上表里只有一行是
在两个 carrier 都没有受损的情况下对比它们的**——`clean`，TCP carrier 的尾部紧四倍。默认行为是先试 mhd、
建不起会话时回退 TCP，那说的是**能否建立**，不是**谁更快**。

这张表**没有**说两件事。它没有把任一 carrier 与其它工具对比——那是 sweep 的事，而同一个 `clean` cell 上
peer 的 p50 是 1.02–1.09 ms、molehill 两个 carrier 是 2.63–2.82（原因见上面"carrier 轴现在是路径条件"
一节）。而且它是容器里的 loopback：丢包与抖动 cell 是塑形的，clean 那个不是，所以 `clean` 是真实路径对
两个 carrier 影响的下界。

### 冷与热

分阶段日程的**第一个** stage 和**最后一个** stage 携带**同一个条件**,而它们在中位数上
相差六倍。两个数字都是真的,而且回答的是不同的问题:

| | p50 | p90 | p99 |
|---|---|---|---|
| 启动几分钟后的第一个 `clean` 阶段 | 12.13 ms | 51.65 ms | 103.70 ms |
| 同一次运行最后的 `clean#2` 阶段 | **1.87** | **2.27** | **15.07** |

对照同一格上的 TCP(p50 2.24 ms、p99 2.58):**热态下这个 carrier 在中位数与二十分位上更快、
在九十九分位上更慢**,而运行第一个阶段的中位数要比它将来的水平差六倍。所以一个部署是在两种
carrier 之间选择:一种跑起来之后胜过 TCP,另一种在运行的第一个阶段更慢。

**而那个阶段的代价不是启动代价。**在它之内延迟是**上升**的:该阶段最初二十次抵达是 2.14 ms
——正是 carrier 保持的速度——其余几百次是 72.78 ms。启动代价会呈现相反的走向。所以表里那
十二毫秒是一个「先快后慢」的阶段的平均值。

**它花在哪里是量过的,靠的是同一秒之内的两个分布。**在 `MOLEHILL_MHD_STATS` 之下,抵达的每一段
都按同一个刻度计时:

| 段 | p50 | p99 |
|---|---|---|
| 接受访客 | 15 µs | — |
| 开一个通道(放置、Noise 握手、前导) | **1.73 ms** | 4.66 ms |
| 等一个通道被提供出来 | 0.95 ms | **20.1 ms**(现在 7.6) |
| 在其上写配对命令 | 2 µs | — |
| 配对之后访客的第一个字节 | 13 µs | — |

**尾部曾是一个带抽签的队列。**等一个通道的时间比整条路径上其它所有段加起来还长——客户端
自己那一侧在中位数上只有 2.1 ms、最坏 7.3 ms——原因是队列在**每次抵达**时唤醒**每一个**在等的
配对,而只有一个能拿到。每次抵达十次唤醒,于是访客的等待就是它输掉多少次抽签:中位数输约五次,
最差的那百分之一输约一百次,这正是量到的十九毫秒。现在通道在前导里用四个字节点名请求它的那次
访问,只投递给那个配对。带孪生的交错 A/B 把 `churn-16` 的 p99 从 **21.95 降到 10.27 ms( −53 %)**,
配对自身的 p99 降到 **7.6 ms**;中位数从 2.93 升到 3.71 ms,因为旧的中位数是向别人借的,
现在它才是一个通道真实的代价。

有两个解释被记为**排除**而不只是「未证」。拥塞窗口在头一秒内就到 2 MiB 的慢启动上限,无法解释
一个整阶段都差六倍的中位数。握手单独也不是答案:它是「一次开流」的代价,而队列是它的乘数
——这正是把开流减半的那几次派生尝试移动了尾部、却没有关掉它的原因。

只测第一个阶段的日程会报告冷数字,只测最后一个的会报告热数字。这个日程**按顺序测两者**,
这正是「顺序是方法的一部分」的原因。

从车道自己的握手派生每条流的密钥来去掉这次握手,做过三次。它把尾部压到 3.79 ms,
抵达速率翻倍、每 bit CPU 减半,而**每一个版本都让 bulk 格付出代价**——是样本直接失败,
不是需要地板才能判断的百分比。所以通往抵达parity的路是存在的,而一个同时保住 bulk 格的
版本暂时没有。流量以短连接为主的部署,在选择 carrier 之前应该先量自己的路径;连接被复用的
部署没有东西可换。

## 透明 L3 的线上开销问题(验收 harness)

L3 客户端承载的是整个 IP 包,所以"线上有多少是首部、其中又有多少能被压缩拿掉"
这个问题有它自己的仪器:`bench/src/bench/utils/l3/run.sh` 在每个臂前后,于各自命名空间内
采样 `/proc/net/dev`;`bench/src/bench/utils/l3/wire_report.py` 把差值换算成承载包的大小
与一个上限。两个接口是关键——客户端拨向服务端的那对 veth(隧道的线上流量,双向,
包含载体自己的 TCP/IP 首部)与两个 TUN 设备(L3 路径真正承载的包)。分母每次都写明:
**wire** 是 veth 的字节数,即链路真实成本;**carried** 是这些包加上本协议 2 字节的
长度前缀。该 harness 跑的是 IPv4;IPv6 共用帧与 GSO 路径,但基础头是 40 字节,所以
这些上限数字是 IPv4 的。`just l3-accept-ipv6` 是 IPv6 的功能验收,不是测量。

| 臂(各自一条连接) | 承载 | 平均承载包 | 线上 | 每个承载包的线上字节 | 首部压缩上限 |
|---|---|---|---|---|---|
| bulk:回显 200 000 B | 434 包 / 422 584 B | 974 B | 493 633 B | 1137 B | 线上的 3.1%(承载的 3.6%) |
| small:2000 次 64 B 往返 | 4010 包 / 464 536 B | 116 B | 785 983 B | 196 B | 线上的 17.9%(承载的 29.7%) |

上限是 `35 B × 承载包数`,是**上界**而不是实测值:IPv4+TCP 首部为 40 B(每台 Linux
主机都会发的 timestamps 使其变成 52 B),VJ 式的按流 delta 约 5 B;这里假设每个包都
可压缩,而每条流的首包、ICMP 与分片都会各自吃掉一部分。

这些数字决定了什么:**首部压缩没有实现。** 在为它而设的小包臂上,上限低于当初
写下的 20% 线上字节门槛。原因就在同一张表里:每个承载包 116 B 却要占用 196 B 线上
字节,说明隧道自身的传输开销约为每包 80 B(本协议 2 字节长度、复用层帧、载体的
TCP/IP 首部及其确认),是压缩 40~52 B 首部所能收回的两倍以上。bulk 臂的上限只有
3.1%:包是满长的,几乎没有首部占比可赢。

### 同一套仪器随后改掉了什么

下面每一项改动都是因为上面那张表点出了成本才做的,而且都用在它要推动的那个臂上
测量。相对增量来自当时 harness 用的 debug 构建;绝对速率来自 **release** 构建——
那才是运维实际运行的,而两者相差很远(bulk 臂 debug 测得 783 Mbit/s,release 是
1986)。

| 臂(release 构建,单主机) | 吞吐 | 每承载包 CPU | 同样负载、不走隧道 |
|---|---|---|---|
| bulk:200 MB 按 65 KB 分块流式传输,TUN MTU 1400 | 1986 Mbit/s | 6.0 µs | 12 024 Mbit/s |
| 同上但 TUN MTU 8000(链路 9000) | **3579 Mbit/s** | 18.4 µs(2.3 ns/字节) | 11 722 Mbit/s |
| 有节奏:2000 次 64 B 严格往返 | 10 362 往返/秒 | 29.9 µs | — |
| 16 条流:同样往返 16 × 200 | 22 543 往返/秒 | 32.0 µs | 23 388 往返/秒 |

每一项改动买到的东西,都列在暴露出该成本的那个臂上:

- **写入侧批量**(多帧一次写入):bulk 臂线上字节少 12%。对有节奏的一来一回没有作用,
  因为它等不到第二个包——批量在设备读空的那一刻就交出,所以合并不付延迟代价,没东西
  可合并时也自然没有收益。
- **`mode = "direct"` 作为 L3 默认**:有节奏臂上线上少 6%、CPU 少三分之一、每秒往返
  多 65%。一条认领只有一条通道,多路复用的帧头是纯逐包成本
  (见[配置文档](configuration.zh.md#透明l3服务))。
- **读取侧也批量**(一次 socket 读取,再从缓冲里解出一串帧):bulk 臂吞吐 +27%、
  每包 CPU −56%,因为一串包不再每帧付两次 await。

**并发会自己形成批量**:16 条流时该臂跑到其对照的 96%(直连服务 23 388 往返/秒),
一行代码都没改,因为包自己就排起了队。这也正是"每 CPU 一个队列"被放弃的原因:并行
TUN 队列只会并行一个并非繁忙主机瓶颈的设备读取,而对照让这句话可以被检验,而不是
听起来合理。

**剩下的是逐包系统调用成本——而设备内的包大小,现在是我们能改的了。** 对 release 构建在
bulk 臂期间做 `perf` 采样:**84% 的 CPU 在内核**,molehill 占 10%,libc 占 5%,没有任何
符号超过 11%——成本就是每个包一次 TUN 读、一次 socket 写、一次 socket 读、一次 TUN 写,摊得
很薄。没有可修的用户态热点——同步数据面只会去抓那 10%,而不是那 84%——真正能推动它的
杠杆是**包大小**:
- **设备自身的 offload(代码改动,v0.11.0 起):** TUN 设备以 `IFF_VNET_HDR` 附加并声明
  `TUNSETOFFLOAD`,内核随即将 TCP 超级帧整块交给读端,而不是先分段。自协议 v5.1
  起,这条 `Vnet` 线格式只在两端都是开启 offload 的 Linux 时协商;只要有一端是纯
  IP 设备就协商 `Ip`,由 Linux 侧在边界处分段/校验——这些 Linux 对 Linux 的数字
  不覆盖那条路径。在一条路由转发路径上
  实测(两个 netns、一跳 TUN、帧整体中继):同样 3.85 GB 的 bulk TCP,无声明时以 576 071 次
  1500 字节读抵达;有声明时以 59 160 次平均 65 212 字节的读抵达——读次数与字节数之比,等于
  下文 8000 字节 MTU 这个运维杠杆买到的东西,只是这次由二进制自己拿到,而不依赖部署。本内核
  上 UDP GSO 即便有声明也在读端之前分段(UDP offload 在这里只有发送侧),所以收益是 TCP 形状
  的;探针在
  [`bench/src/bench/utils/l3/tcp_tso_census.py`](../bench/src/bench/utils/l3/tcp_tso_census.py),
  同一版本的线格式长度前缀改为 `u32`,让整个超级帧装进
  一帧。
- **TUN MTU(运维设置):** 同样的字节用 8000 字节的包而不是 1400,实测吞吐 1.8 倍、每字节
  CPU 减半。那是部署侧的选择,不是代码改动:TUN 的 MTU,以及与之匹配的链路 MTU
  (见[部署文档](deployment.zh.md#透明l3服务))。

**出借车道能买到什么,以及在什么条件下。** 下文 L3 各行测的是「认领持有其 carrier 预算
份额所给的车道」;除此之外客户端还会把某条空闲认领的车道**借给**流比车道多的认领(见
`docs/internals.md`「Lanes are lent」)。这件事值不值,取决于路径的瓶颈在哪里,而模型给出了
答案:当条件加在 **carrier** 那一侧(100 ms 隧道腿,于是认领的吞吐由每条连接限制)时,把八条流
铺到空闲认领借出的车道上,对该认领值 **+27%**(2.395 对 1.754 Gbit/s,十轮,按模型自身的规则构成 claim:
materiality 10%、符号一致 1.0,并且越过本轮 A/A 地板)。同样比较在 1% 丢包下是 +12%、属
**定向**:效果在丢包下依然存在,但十轮还无法把它与波动分开;而在干净 loopback 上完全落在
噪声里。它买到的是吞吐而不是效率(每字节 CPU +8%、CPU 核数 +32%、峰值 RSS +11%,均为定向)
——用更多连接承载更多流量。条件加在访客腿、或干净 loopback(此时 L3 路径是按包受限)时,差异落在噪声
里。复现用的是**臂**而不是另外构建的二进制:目录里就有 `l3-budget10`(开着出借)与
`l3-budget10-nolend`(同一拓扑、同一个二进制,只是 `[transparent.data].lend = false`),
所以 `just bench run --arms l3-budget10,l3-budget10-nolend --condition rtt100
--condition-leg tunnel` 就是全部实验;完整记录在 `HANDOFF.md`。

**给多路复用开销做归因。** 上面 L4 各行说明多路复用要花多少(池上单条流大约只有独占连接的一半吞吐,而每字节 CPU 约为两倍);这些 CPU 去了哪里,由 `bench/src/bench/utils/mux/gap_profile.sh` 回答:它用 `perf` 在一条 iperf3 流穿过一条隧道时同时采样两端守护进程,并按守护进程打印最热的符号。本机上的形态是:**约 35% 在内核、约 15% 在 libc 的内存例程、mux 自己的 Rust 代码每个符号只有几个百分点**——每个叶子都很小,总量落在「每字节要拷贝几次、要几次系统调用」上,而不是某个热点函数。这与下文 TUN 路径得到的结论一致,也正是候选方案都是结构性的原因(一个包被拷贝几次、一次成帧写入多大),而不是去优化某个函数。

**方法说明:bulk 臂曾经测的是一次死锁。** 它先发一整块再读回显,超过缓冲就必然卡死
——访客等回显,回显等访客读——其中 20 MB 与 100 MB 的两次运行被当成吞吐报了出去,而
实际是五秒的超时停摆。该臂现在按 `BULK_CHUNK` 分块流式传输,同样跑满尺寸的包但不
会死锁;`PROFILE_BUILD=release` 选择构建(默认 `debug`,因为编译最快)。来自这套仪器
的数字如果不写构建,就不是一个数字。

**可比性。** 单主机、无整形、每臂一条连接,测于 `9507a7a` 与本次修订之间;各臂彼此
可比,与其它任何数字都不可比——尤其是与上面的 soak 数字,后者用另一套仪器、整形过的
路径与大量连接。该仪器仅限 root,位于检查链之外(见 [checks.md](checks.md));
用 `just l3-accept` 复现,产物目录里的 `bulk.report` / `small.report` 就是原始输出。
它的仪器参数是环境变量覆盖,因为它们会改变数字的含义:`BULK_BYTES`(默认
200 000;当 CPU 计数器 100 Hz 的分辨率重要时,把它提到一秒以上的流量)、
`SMALL_REQUESTS` 与 `SMALL_BYTES`(默认 2000 × 64 B)、`CLAIM_LANES`(不设置,即测量
产品自身的默认值——每条认领一条承载连接;设为更大的数字会把该认领的流铺到那么多条
连接上),以及 `CLAIM_LANE_CAP`(不设置;设成小于 `CLAIM_LANES` 的值,即测量服务端
`[server.data].max_tunnels` 阀门拒绝认领多余车道、而认领用剩下的车道继续
服务的情形)。

## UDP 队列问题(仅 molehill 的诊断)

UDP 服务的数据报上限是**服务**的属性,不是阶段日程的属性,所以它有专门的仪器:
`bench/src/bench/utils/udp_stress.py` 启动真实的一对进程(`max_udp_workers` 可配),用**限速或
全速**的访客打它,并在每一步前后读取服务端的 `MOLEHILL_UDP_STATS` 行;最后一步是
对照——同样的访客**直接打 sink**。没有这个对照,慢 sink 和慢隧道从计数器上看是
一样的。同一主机、1400 字节数据报实测:单个访客从不丢包(它自己的 socket 缓冲把它
限在约 29.8k 数据报/秒),多访客把池打到约 1 Gbit/s 饱和,与 `max_udp_workers`(1/2/4 分别
1.14/1.00/0.98)和访客数都无关,扩散保持均匀,而丢弃量与该上限之上的超出部分相差
0.07% 以内。用户需要的数字在配置页 `max_udp_workers` 旁边。背后的探针是
`bench/src/bench/utils/udp_stress.py`;用同样的方式运行,就能在自己的主机上复现这个上限。

## 可比性
- **同模型、同方法、同主机。** 每份结果文件都记录指纹、主机身份与两个校准探针;
  来自另一台主机或另一个方法的数字只是背景,不是基线。
- **比较是被拒绝,而不是被近似。** `just bench compare` 会点名每一条阻断理由
  ——某个方法键有差异、某个探针缺失、某台主机的分歧超出它的容差(CPU 探针
  25%,loopback 探针 15%;与 gate 用的是同样这两个探针)——而一轮没有 A/A 对的
  运行,会把文件之间的每一处差异都报成 `directional`,绝不报成 claim。
- **在同一场战役之内,各臂按构造就是可比的**:一条拓扑、一个后端、每个臂一个
  二进制、一次轮转,且每一轮都有一个对照。
- **soak 记录是历史,不是基线。**
  `benches/records/results-soak-vX.Y.Z.json` 是用本模型所取代的那个模型测的:不同
  的 schema、不同的仪器、不同的格子定义。gate 拒绝把它当作基线,而已发布表格里
  的数字就作为当时测到的东西成立,而
  [逐项实测表](#每个配置选择的代价逐项实测)
  是配置之间做选择时唯一仍然成立的依据。
- **方差是如实陈述的,不是抹平的。** 如果某个差异落在本轮运行自身的各道下限之
  内,就按 indistinguishable 上报,不从中得出任何 claim。
- **阶段按出现次序比较,不按名字。** 日程以同一个 `clean` 条件开场也收尾,所以
  `clean#2` 与另一轮的 `clean#2` 相比:返回阶段——恢复轴——是照着基线的*返回*
  判的,不是照着它全新的时候。
- **tunnel pool 是固定的,所以它的尺寸*就是*一个设置。** 一个构建在服务启动时
  建立 `[client.data].tunnels` 条连接并保持它们(死亡的会被修复)。
  `MOLEHILL_POOL_STATS` 行会把配置的 `count` 报在存活的 `size` 旁边:`size` 低于
  `count` 的 pool 就是修复正在被拒绝的 pool,而一个 arm 的宽度和它的 carrier
  一样,也是一个方法参数。

## 自己复现

在一台装有 `iperf3`、`tc` 并且有 root 的 Linux 主机上(见 `just bench-deps`):

```bash
just bench doctor                      # is this host ready?
just bench peers fetch                 # the reference tools' release binaries
sudo -n just bench --profile dev --aa  # a change, measured
just bench plot ~/tmp/bench-*.json     # its charts and tables
```

发布 sweep 是一条命令,门禁是另一条:

```bash
sudo -n just bench --profile sweep --out benches/records/results-bench-vX.Y.Z.json
just bench gate benches/records/results-bench-vX.Y.Z.json \
     --baseline benches/records/results-bench-v<previous>.json
```

`just bench run --help` 会列出各 profile、各臂、各条件与各旋钮;`just bench list` 打印
注册表;而每一个会改变数字含义的参数都记录在结果文件里(解析后的场景参数、条件、
时间线、各仪器的节奏、SLO),因此任何一张图总能追溯回产出它的方法。

发布门禁——一个公开的数字在被某个 tag 带上之前必须满足什么——见
[release.md](release.md)。
