## 测量的是什么

测的是**时间上的工作负载**,而不是每个网络条件一个平均值。每个工具都被驱以
完全相同的客户端侧工作负载——1 条交互流(每次 ping 新建一条 TCP 连接:声明
SLO 所用的那件仪器)、N 条 bulk TCP 流、稳定的短连接速率,以及 1 条 UDP 会
话——同时路径按脚本化的网络条件日程推进。工具的进程只启动一次,整形原地切
换,因此会话从不重建:一个工具*如何适应*先劣化、后恢复的路径,本身就是测量的
一部分,而不是藏在测量之前的预热成本。

一切都从工具外部观测(吞吐与每区间重传来自 iperf3,RTT/丢包/抖动来自探针,
RSS / CPU / 打开 fd / 线程数来自 `/proc`)。这正是对端能用同一份工作负载被测
量、并被画进同一批面板的原因——也正是 molehill 自己的内部计数器从不出现在比
较中的原因。

测量是单机的:访客、服务端、客户端与后端同居一台主机,网络条件作用在回环路
径上。因此绝对吞吐描述的是*这*台主机;能迁移到别处的是形状、排序与 SLO 行为。

交互流的 p99 在 **50 ms** 以内、错误率不高于 **0.5%**,这就是 SLO:它是
`capacity` 测试的中止条件、每张图里的虚线,也是发布门禁在 clean 阶段检查的东
西。劣化阶段*本应*远高于它——那正是测量本身,而不是失败。

错误项取一个比率而不是「零」,是因为在这个场景里零并不是工具的属性:一轮四臂
测量在各自的 clean 阶段得到 frp 0、rathole 0.05%、molehill 0.07%、nps 0.31%,
若以绝对零为线,散度中点会被标成发布阻断,而两条参照臂比它还差。0.5% 高于迄今
测过的所有臂,又远低于用户能感知的程度;某一轮可以用 `SOAK_SLO_ERROR_RATE` 把
它收紧。

## 怎么读这些图

- **SLO 线(虚线)。** 一条路径要被算作可用,交互流必须把 p99 保持在 50 ms
  以内、错误率不高于 0.5%。它是每张图共有的那根线。
- **响应时间的纵轴是对数的。** 劣化路径要付出三个数量级的代价;若用线性轴,
  健康阶段会根本看不见。
- **阴影带是路径档**,名字标在顶部;绿色带是未整形的对照阶段,灰色带是被刻
  意劣化的阶段。最后一条带与第一条是同一个 clean 条件:**恢复轴**。
- **底边的红条是一次 wedge**——交互流静默(完全没有响应)超过五秒。它的时
  长印在面板一角。始终停在 wedge 的工具是一个发现;能恢复的那个才是更有用
  的答案。
- **实线与虚线是逐阶段的分布**:实线阶梯是每个阶段的中位数,虚线是它的
  p99。之所以两者都给,是因为几万个样本的散点会盖掉摘要,而摘要又会盖掉离群
  点——两者你都要。
- **小倍数图**(`soak-<version>-stages.png`)直接回答比较问题:每个条件一个
  面板,每个工具一根棒棒糖(圆点 = 中位数,横杠 = p99,竖线 = 最差一秒)。
  一个 `x` 表示该阶段没有为那个工具产出任何样本。
- **漂移图**会印出每条线的拟合斜率,因为泄漏是随时间的斜率,而不是一个水
  位:一条高但平的 RSS 线不是泄漏,缓慢爬升的那条才是。

### 怎么读一个格子

- **阶段的 bulk 格是整个窗口上的负载,并且标明是哪一侧测出来的。** 读数取发送侧
  在该阶段测量窗口内的字节数、按区间跨度加权——不是它最好的那一秒,因为 netem 会
  把一次突发送进它选中的任意区间,峰值因此是整形器日程的属性。决定哪一侧说话的是
  **测量本身,而不是档位**:当发送侧的记账失效时——客户端的 `end` 事件这么说,或该
  阶段有一半以上区间读数为零字节,也就是 socket 缓冲把整段负载吸了进去——读数取
  **接收侧自己的窗口**,图表与 README 用 `*` 标出;若连接收侧汇总也没有,该格**就是
  没有读数**,并写明原因,而不是拿失效的那一侧充数。某一格用了哪一侧与它一起记录
  (`bulk_gbps_source`),回退留给仍然需要它的格子(`jitter`)。
- **整形档的交互格是背景,不是判定。** 主导它的是 harness 自己装上的 netem 队列,
  而单轮并不重复:在本机上用同一套未改动方法跑三轮,整形档的 p99 格移动 5-24%
  (双腿作用范围下最高 48%),而 gate 对单阶段 p99 用的限值是 25%。因此 gate 对
  整形档只**上报**数值、只对暴涨(3 倍以上)判失败,而 README 把这些列标成背景,
  不在其中挑赢家。
- **没有读数的阶段会说明原因。** 图表表格里的 `— (reason)` 与结果文件里的
  `bulk_gbps_source`,把"路径什么都没承载"与"没有人能测出它承载了什么"区分开;
  一个光秃秃的 `0` 做不到——那正是记账失效的发送侧对一条满载路径给出的数字。
- **每个阶段的数字都带着自己的样本数。** 一个阶段的 `rtt_p99` 是该阶段交互样本的
  nearest-rank 百分位,所以样本不足一百时,"p99" *就是*最差的那次观测——饱和运行
  中被整段楔住的阶段往往只有几十个样本,此时报的是最差单次测量而不是尾部估计。图表
  用 worst-second 刻度标出它;结果文件每阶段都带 `rtt_n`,读者因此能分辨一个格子是
  哪类数字。

## 阶段日程

### 时间线

这是默认日程——`capacity` 与 `rrul` 跑的那一条。另外还有三种日程,某一轮用
的是哪一种,记录在它的结果文件里(`meta.timeline`,与路径档记在一起):

- **`soak`** 用一条更短的日程轮转更长时间:`clean` → `loss1` → `rtt100` →
  `loss5` → `clean`,每段 180 s;
- **`cost`** 与 **`screen`** 只跑单个阶段——`--path` 加 `--secs`(默认 60 s);
- **任何测试**都可以显式传 `--timeline clean:60,loss1:120,...`。

| 阶段 | 模拟什么 | 施加到路径上 | 时长 |
|---|---|---|---|
| `clean` | 健康网络(对照) | 无 | 150 s |
| `rtt100` | 长途或卫星链路 | 100 ms 延迟 | 120 s |
| `loss1` | 有丢包的 wifi 或移动链路 | 10 ms 延迟、1% 丢包 | 120 s |
| `loss5` | 严重拥塞的路径 | 100 ms 延迟、5% 丢包 | 120 s |
| `rate100` | 100 Mbit 上行 | 100 Mbit/s、20 ms 延迟 | 120 s |
| `rate20` | 20 Mbit/s 上行 | 20 Mbit/s、40 ms 延迟 | 120 s |
| `jitter` | 缓冲区膨胀的接入链路 | 20 ms 延迟 ± 10 ms | 120 s |
| `clean` | 恢复——工具还是原来那个工具吗? | 无 | 150 s |

日程、时长、采样率与 SLO 都记录在每份结果文件里(`meta`),因此任何一张图总
能追溯回产出它的方法;每个档位施加的整形参数也在其中——包括限速档的队列深度
(`rate`/`limit 2000`),它决定整形器最多能压住多少流量,因而也决定了一次突发
穿过它能造成什么。

### MTU 档位

另有两条路径档承载**分片**这一维,它们刻意不出现在任何默认日程里:

| 路径档 | 模拟什么 | 施加到路径上 |
|---|---|---|
| `mtu1280` | 隧道,或 IPv6 最小可容忍路径 | 接口 MTU 1280 |
| `loss1_mtu1280` | 既丢包又会分片的链路 | 10 ms 延迟、1% 丢包、接口 MTU 1280 |

MTU 是**接口**属性而非 qdisc:使用这两档的阶段会改变该阶段内 **`lo` 上每一个
包**的路径——包括对端的、harness 自己的、以及工具控制面的包。这也是它们不进
默认日程、只作为专注的单阶段格运行的原因(`--test=cost --path=loss1_mtu1280`,
或用 `--test=screen --path=…` 在同一格上 A/B 两个构建)。`meta.mtu_restore_to`
记录运行开始时接口的 MTU,harness 在收尾时恢复它,恢复失败会**报错**而不是沉
默——残留的 1280 会毒化该主机之后每一次运行。这一维存在的理由:`lo` 的 MTU 是
65536,没有它任何数据报都只占一个分片,"丢失一个分片的代价"根本无法测量。读这两
档时请与下面的 `carrier = "kcp"` 一行合看。

### 整形作用范围与开关

**档位只施加在访客那一腿上**(`SOAK_SHAPE_LEGS=visitor`,默认)——即工作负载
拨号的那一组暴露端口——另外对 KCP 载体再加上隧道自己的 UDP 端口(那是 harness
在链路上唯一能指名的隧道)。因此每一次注入延迟只付一遍。工具的 backend 腿(客
户端进程到它转发的后端)不整形:真实部署里 WAN 在访客这一侧,后端就在工具旁边。
`SOAK_SHAPE_LEGS=both` 把整形也扩展到那条腿;某轮实际用的是哪个值记录在它的
`meta.shape_legs` 里。

只有数据面被整形。工具的控制通道留在未整形的路径上:整形它会打死心跳,把一
次容量测量变成一场 wedge 研究。

**限速档会限制 bulk 客户端的 socket 窗口**(`SOAK_RATE_SOCKET_WINDOW`,默认
`256K`;`off` 关闭这一限制)。不加限制的发送侧会破坏自己的记账:它的写入会先灌
进一个远大于整形路径排水能力的 socket 缓冲,于是测量区间读到零字节而路径仍在承
载;客户端还可能在阶段边界之后仍被阻塞,连它自己的汇总都到不了。有界窗口让写入
跟随路径。它只作用于限速档:只有在路径速率已知的地方,窗口才有意义;在纯延迟档
或 clean 档上它会压住带宽时延积,改变它本应服务的测量。

### 阶段交接

**上一个阶段彻底安静下来之前,下一个阶段不会开始。** 阶段边界会杀掉 bulk 客户
端,而被杀掉的 TCP socket 仍会把内核侧还在排队的数据交付出去,也会带着 FIN 一
直重传——用的还是当时挂着的那个 qdisc。此刻换整形,就是把上一个阶段的收尾排进
了下一个阶段握手的同一个队列;又因为一个工具的所有数据面端口共享同一个 netem
class,一个被这堆收尾数据挤掉的 SYN 会让下一阶段开头几十秒报废。于是 harness 会
在**旧**整形下等待:直到路径按两个测量都算安静——排队不超过一帧(`64 KiB`,即
`lo` 的一个 MTU)**且**吞吐端口上没有任何处于"还能发包"状态的连接(`ESTAB`、
`FIN-WAIT-1`、`CLOSE-WAIT`、`SYN-SENT`、`SYN-RECV`)——两者都连续两次采样成立,
之后才施加下一阶段的整形。

两半都取容差。队列**永远到不了零**——交互、churn 与 UDP 探针和工具共用同一个
class,会永久留下约 1.2 KB——所以一个等"队列恰好为空"的 drain 只能靠耗尽预算结束,
整个交接也就变成**定时器驱动**,起始状态取决于时钟而不是取决于路径。"没有连接"
也不能等于"没有非 LISTEN 连接":`FIN-WAIT-2`/`CLOSING` 会滞留**数分钟**且不承载
任何数据,而上面列出的恰恰就是会重传被杀 bulk 客户端内核里那几十 MB 的状态。队列
那一半判据是**读出来的**,不是假设出来的:`tc` 渲染 backlog 时带单位后缀
(`b`、`Kb`、`Mb`、`Gb`),drain 先把它解析成字节,再作任何判断。

`SOAK_DRAIN_BUDGET`(180 s)是**安全网,不是机制本身**,取值高于本模型上实测的最
差交接:等待由判据结束,安全网被触发会被记录,而不是被悄悄吞掉。这次等待花了多久、
留下了什么,都随它后面的那个阶段一起记录(`drain_s`、`drain_expired`、
`drain_final_backlog`、`drain_busy_sockets`);脊柱自己看到的交接状态也一样
(`spine_sockets`,两条吞吐链路都有;`backend_restart`、`spine_attempts`、
`spine_first_interval_s`)——一次耗尽预算的 drain,会让下一阶段的 bulk 从一个被记
录下来的状态开始,而不是一个只能靠猜的状态。

交接**未必**能很快变安静,因此脊柱会按
`SOAK_SPINE_RETRY_S`(阶段内的秒数,默认 `0,25,50,80`)多次拨号,在第一次真正产出
interval 的拨号处停止;而一个**什么都没产出**的拨号会在下一个偏移点被放弃,
免得一个卡死的拨号吃掉它本应留出的那次重试。`spine_attempts` 是拨号次数,
`spine_first_interval_s` 是 bulk 真正开始的时刻。同样地,单测模式的 `iperf3` 后端
在**每个阶段**的 bulk 尝试之前、以及任何一次采样失败之后都会重启:一次收尾落在它
身上会让它此后对每次连接都回 `Bad file descriptor`,之后所有拨号都会挂住——重启
本身也会被记录。

## 测试类型

`--test` 接受逗号列表,因为一份产物可以承载多种类型:发布扫描跑的是
`rrul,capacity`,于是阶段日程与负载斜坡装在同一个文件里(同一份 `meta`、同一台
主机、同一个修订)。它们是**两把不同的尺子**,绝不互相印证:日程回答"路径随时间
变化时会发生什么",斜坡回答"在 SLO 被打破之前它能扛多少"。文件里每个测试条目都
带自己的 `test` 类型,gate 也只按同类型相比(按工具*和*测试类型配对)。

| 类型 | 它回答的问题 |
|---|---|
| `capacity` | 在一条全新的交互连接仍满足 SLO 的前提下,工具能承载多少 bulk 负载?(可持续负载 + 完整响应时间曲线) |
| `rrul` | 饱和状态下,路径随时间变化时,新访客的延迟会怎样?(README 里的那张图) |
| `soak` | 在轮换路径上长时间运行:有没有东西泄漏、漂移或退化? |
| `cost` | 在固定工作点上,每承载 1 Gbit/s 要花多少 CPU 秒? |
| `screen` | 针对一次开发改动:两个构建之间——或同一个构建的两种配置之间——的差异是 claim 还是噪声? |

按需诊断开关(`MOLEHILL_MUX_STATS`、`MOLEHILL_KCP_STATS`、
`MOLEHILL_POOL_STATS`、`MOLEHILL_PLACEMENT_STATS`、`MOLEHILL_UDP_STATS` 与
`MOLEHILL_STRIPE_COUNT`)属于设置,记录在
[configuration.zh.md](configuration.zh.md#诊断开关按需开启)里;每个仪器
逐行的内容就是 [internals.md](internals.md#the-tunnel-pool) 里的 S1 记录。某一
轮继承了哪些开关会记进结果 meta(`instrumentation`),因此带仪器的一轮不会被误
认为干净的一轮。

### 隔离单一变量的两种方式

阶段日程是把一个工具与它的对端相比。下面两种交错模式则是把某个东西与它自己相
比,而这正是开发决策通常需要的:两条臂都跑在同一轮的每一个负载步里,因此看到
的是同一份机器状态;靠先后两次运行来做前后对比会被 epoch 漂移打败,本仓库从
不用它来决定任何事情。

- **`--ab BIN_A,BIN_B`**(配合 `screen`)在每个负载步交换两个*构建*。
- **`--ab-variants VAR_A,VAR_B`**(配合 `screen`)以同样的方式交换*同一个二进制
  的两种配置*:一个构建、两份配置。某个配置决策——例如 `direct` 与共享池——
  就是这样被测出来的,不会让构建这一维混进来。这一维记录在结果文件里
  (`meta.builds.axis`),判定工具也会把它打印出来,因此读者不会把一对配置误读
  成一对构建。

**只要该轮同时带着两个指标,吞吐与交互 p99 就各有自己的表和自己的判定。**
判定要求每个指标各自"每一步同号**且**至少 15%"。

两者在不适用的地方都会被拒绝而不是被默默忽略:`variant` 这一对只对 `screen` 有
意义(其余测试类型全程只跑一种配置),而把 variant 名字写错会被拒绝,而不是拿
一种配置去和它自己比较。

### 慢访客(`SOAK_SLOW_VISITOR_BPS`)

默认关闭。设置之后,每个阶段还会运行一个慢访客:一条连到工具 echo 服务的连接,
按给定速率把响应读回来,于是整个阶段里回程都处于背压状态。它存在的目的是让队头
阻塞变得可测——一个慢访客的流是否拖慢了与它共享同一个池的那条交互流——而它旁边
要读的数字是**该阶段的交互 p99,绝不是访客自己的速率**:被限速的读取者只会报告
你给它的那个旋钮值,所以它的序列是失速探测器(低于旋钮值的阶段才是发现),不是
容量数字。

被注入的访客是工作负载的一部分,因此带它的那一轮记录的是**不同的方法版本**
(`meta.workload_version`:不带为 1,带为 2)。门禁因此拒绝把带探针的一轮与不带
探针的一轮相比较,也拒绝比较两个速率不同的探针轮次。与其它探针一样,它跑在自己
的进程里——harness 绝不进入它正在测量的路径——它的结果按阶段记录
(`completed` / `failed` / `killed` 加类型化原因),并且从不让整轮失败。`reconnect`
拒绝它:那个测试量的是冷启动,不是工作负载。

## 本模型回答不了什么

写在这里,免得读者向一张图索要它从未测过的东西:

- **每阶段只有一个样本。** 一个阶段的数字来自对该日程的一次遍历,所以单轮无法为
  只访问一次的档位给出自身重复性。日程会两次访问 `clean`(本轮自己的重复实验,由
  `just soak-check` 报出),而整形档的重复性是单独测的:同一套未改动方法三轮,整形
  档 p99 格移动 5-24%,bulk 格移动 0.2-3%。
  比该档自身离散度更小的跨轮差异,不是一对运行能分辨的——那正是 `screen` 互嵌模式
  的用途,也是 `soak-check` 干脆不对整形档做差值判定的原因
  (见[怎么读一个格子](#怎么读一个格子))。
- **两个臂都贴在 loopback 上限上。** 在单机上,量程的顶端是 loopback 路径本身,
  而不是工具,所以够到它的臂无法靠单轮运行分出先后。同一份未改动的代码(各轮之间
  只有测试与文档变化)三轮 sweep 下来,这里够到它的两个臂读到 15.9-22.2 与
  12.8-20.4 Gbit/s——摆动达 39 % 与 59 %,足以让两者的先后**反转**;而比上限低
  一个数量级的 `frp`(6.04-6.19)与 `nps`(0.133-0.136)变动不到 3 %。同几轮里
  主机自己的 loopback 探针始终落在 21.6-21.9 Gbit/s 之内,所以这个摆动不是路径。把这两行
  读作对主机状态的一次读数,永远不要把它们的先后当成可以长期引用的结论,也永远
  不要把两者之间的跨轮差异读成代码变化。
- **退化路径下的控制面。** 被整形的只有数据平面;工具自己的控制通道留在未
  整形的路径上,因为整形它会把一次容量测量变成一次 wedge 研究。控制通道在
  丢包*之下*的任何行为(心跳存活、重连)都在本模型射程之外。
- **工具自身的内部状态。** 被测量的一切都是外部可观测的,所以对等工具与
  molehill 以完全相同的方式被测量——两者的内部计数器都不会进入对比。可选
  的 `MOLEHILL_*` 开关给一轮运行加上 molehill 专有的诊断,继承了任何一个开
  关的运行会把它记进 `meta.instrumentation`。
- **一个 peer 数字描述的是哪个配置。** 已发布的四工具表是 molehill 的**默
  认配置**(plain 传输、`multiplex` 模式、每服务一个池)。共享弹性池
  (`--variants shared`)、Noise 传输、KCP 载体与 `direct` 模式是另外的 arm,
  下面的逐项实测是它们之间做选择的唯一记录在案依据。

## 每个配置选择的代价(逐项实测)

弹性池自身的阈值——一条隧道的流容量达到 12%(64 条中的 7 条)时增长、56 条
时拒绝放置、5 分钟没有任何字节流动就收割一次转发——是内部常量而不是设置
项,并且只有在测量支持下才会改变:增长阈值来自一次两阶段复现(规则原本要求
一条隧道上 64 条流中的 51 条,而工作负载峰值只有 20-21 条,池因此从未长过一条
隧道),此后每一项都经过后续 sweep 的复核。

| 决策 | 选项 | 实测依据(退役的逐格模型) |
|---|---|---|
| `mode` | `"multiplex"`(默认) | 回环 1 流 10.0 Gbit/s,`direct` 为 19.2;8 流分别 19.5 vs 23.3;multiplex 吸收每连接的建连成本(churn ~4.8k 连接/s)并节省 FD / 端口 / NAT 映射 |
| `mode` | `"direct"` | 原始单流吞吐;每条流一条物理隧道(FD / 端口 / NAT 成本随流数增长) |
| `count` | `1` | 所有流量共用一条隧道:没有聚合,所有流共享同一个重传域(回环 8 流聚合 9.2 Gbit/s,count = 4 时为 19.5;loss5 队头阻塞最大 2.5 s,count = 4 时为 1.6 s) |
| `count` | `4`(默认) | 聚合越过单流(loss1 8 流 12.3 vs 4.5 Gbit/s)并隔离队头阻塞(rtt10 最大间隔 80.6,count = 1 时为 100.1 ms);yamux 上限 `count × 64` 条并发连接 |
| `count` | `8+` | ~512 条并发连接(8 条隧道 × 每条 64 条 yamux 流);每服务 8 条物理隧道(NAT 映射 ×8) |
| `carrier` | `"tcp"`(默认) | 在每一处未被标记的测量里都领先于 KCP 载体(noise 传输下回环 1 流 5.8,kcp4 arm 为 3.7 Gbit/s),内存开销也低得多(RSS 26 vs 85 MiB)。回环 8 流那一格(14.9 vs 1.1 Gbit/s)在这里排除:它在两个构建上跨重复都是双模的,因此不能作为任何结论的依据 |
| `carrier` | `"kcp"` | 仅在 TCP 数据隧道被封锁或限速时,或为了在高延迟路径上 A/B 一个 UDP 游戏:它唯一实测的赢面是 rtt100 的 UDP 会话质量(0% 丢包、最大包间隔 20 ms,TCP 各 arm 为 100+ ms) |
| transport | `"plain"` | 回环 10.0 / 19.5 Gbit/s(1 / 8 流) |
| transport | `"noise"` | 5.8 / 14.9 Gbit/s;RTT 代价亚毫秒;满载下 CPU 持平 |
| `pool_size` | 8 TCP / 2 UDP(默认值) | 16 路 churn 下建连到首字节 p99 ~3.5 ms;UDP 把不同访客分片到不同通道,绝不拆分单个会话(会话亲和) |
| `[server.data].stripe_count` | `K = 4`(条带组把一条访客连接摊到 K 条数据通道上;见[配置文档](configuration.zh.md)) | 单条长连接不再被一条隧道流钉死:回环 1 流吞吐 +48.7%,代价是重排缓冲、RSS +8.7%、CPU +40.8%(每帧 CPU 减半,因为帧摊到了四个驱动任务上) |

## 透明 L3 的线上开销问题(不属于 soak 模型)

L3 客户端承载的是整个 IP 包,所以"线上有多少是首部、其中又有多少能被压缩拿掉"
这个问题有它自己的仪器:`benches/scripts/l3/run.sh` 在每个臂前后,于各自命名空间内
采样 `/proc/net/dev`;`benches/scripts/l3/wire_report.py` 把差值换算成承载包的大小
与一个上限。两个接口是关键——客户端拨向服务端的那对 veth(隧道的线上流量,双向,
包含载体自己的 TCP/IP 首部)与两个 TUN 设备(L3 路径真正承载的包)。分母每次都写明:
**wire** 是 veth 的字节数,即链路真实成本;**carried** 是这些包加上本协议 2 字节的
长度前缀。

| 臂(各自一条连接) | 承载 | 平均承载包 | 线上 | 每个承载包的线上字节 | 首部压缩上限 |
|---|---|---|---|---|---|
| bulk:回显 200 000 B | 434 包 / 422 584 B | 974 B | 493 633 B | 1137 B | 线上的 3.1%(承载的 3.6%) |
| small:2000 次 64 B 往返 | 4010 包 / 464 536 B | 116 B | 785 983 B | 196 B | 线上的 17.9%(承载的 29.7%) |

上限是 `35 B × 承载包数`,是**上界**而不是实测值:IPv4+TCP 首部为 40 B(每台 Linux
主机都会发的 timestamps 使其变成 52 B),VJ 式的按流 delta 约 5 B;这里假设每个包都
可压缩,而每条流的首包、ICMP 与分片都会各自吃掉一部分。

这些数字决定了什么:**首部压缩没有实现。** 在为它而设的小包臂上,上限低于当初
写下的 20% 线上字节门槛。原因就在同一张表里:每个承载包 116 B 却要占用 196 B 线上
字节,说明隧道自身的传输开销约为每包 80 B(本协议 2 字节长度、复用层帧、载体的
TCP/IP 首部及其确认),是压缩 40~52 B 首部所能收回的两倍以上。bulk 臂的上限只有
3.1%:包是满长的,几乎没有首部占比可赢。

### 同一套仪器随后改掉了什么

下面每一项改动都是因为上面那张表点出了成本才做的,而且都用在它要推动的那个臂上
测量。相对增量来自当时 harness 用的 debug 构建;绝对速率来自 **release** 构建——
那才是运维实际运行的,而两者相差很远(bulk 臂 debug 测得 783 Mbit/s,release 是
1986)。

| 臂(release 构建,单主机) | 吞吐 | 每承载包 CPU | 同样负载、不走隧道 |
|---|---|---|---|
| bulk:200 MB 按 65 KB 分块流式传输,TUN MTU 1400 | 1986 Mbit/s | 6.0 µs | 12 024 Mbit/s |
| 同上但 TUN MTU 8000(链路 9000) | **3579 Mbit/s** | 18.4 µs(2.3 ns/字节) | 11 722 Mbit/s |
| 有节奏:2000 次 64 B 严格往返 | 10 362 往返/秒 | 29.9 µs | — |
| 16 条流:同样往返 16 × 200 | 22 543 往返/秒 | 32.0 µs | 23 388 往返/秒 |

每一项改动买到的东西,都列在暴露出该成本的那个臂上:

- **写入侧批量**(多帧一次写入):bulk 臂线上字节少 12%。对有节奏的一来一回没有作用,
  因为它等不到第二个包——批量在设备读空的那一刻就交出,所以合并不付延迟代价,没东西
  可合并时也自然没有收益。
- **`mode = "direct"` 作为 L3 默认**:有节奏臂上线上少 6%、CPU 少三分之一、每秒往返
  多 65%。一条认领只有一条通道,多路复用的帧头是纯逐包成本
  (见[配置文档](configuration.zh.md#透明l3服务))。
- **读取侧也批量**(一次 socket 读取,再从缓冲里解出一串帧):bulk 臂吞吐 +27%、
  每包 CPU −56%,因为一串包不再每帧付两次 await。

**并发会自己形成批量**:16 条流时该臂跑到其对照的 96%(直连服务 23 388 往返/秒),
一行代码都没改,因为包自己就排起了队。这也正是"每 CPU 一个队列"被放弃的原因:并行
TUN 队列只会并行一个并非繁忙主机瓶颈的设备读取,而对照让这句话可以被检验,而不是
听起来合理。

**剩下的是逐包系统调用成本,而它不是我们能拿掉的。** 对 release 构建在 bulk 臂期间
做 `perf` 采样:**84% 的 CPU 在内核**,molehill 占 10%,libc 占 5%,没有任何符号超过
11%——成本就是每个包一次 TUN 读、一次 socket 写、一次 socket 读、一次 TUN 写,摊得
很薄。没有可修的用户态热点——同步数据面只会去抓那 10%,而不是那 84%——真正能推动它
的杠杆是**包大小**:同样的字节用 8000 字节的包而不是 1400,实测吞吐 1.8 倍、每字节
CPU 减半。那是运维侧的设置,不是代码改动:TUN 的 MTU,以及与之匹配的链路 MTU
(见[部署文档](deployment.zh.md#透明服务))。

**方法说明:bulk 臂曾经测的是一次死锁。** 它先发一整块再读回显,超过缓冲就必然卡死
——访客等回显,回显等访客读——其中 20 MB 与 100 MB 的两次运行被当成吞吐报了出去,而
实际是五秒的超时停摆。该臂现在按 `BULK_CHUNK` 分块流式传输,同样跑满尺寸的包但不
会死锁;`PROFILE_BUILD=release` 选择构建(默认 `debug`,因为编译最快)。来自这套仪器
的数字如果不写构建,就不是一个数字。

**可比性。** 单主机、无整形、每臂一条连接,测于 `9507a7a` 与本次修订之间;各臂彼此
可比,与其它任何数字都不可比——尤其是与上面的 soak 数字,后者用另一套仪器、整形过的
路径与大量连接。该仪器仅限 root,位于检查链之外(见 [checks.zh.md](checks.md));
用 `just l3-accept` 复现,产物目录里的 `bulk.report` / `small.report` 就是原始输出。
它的仪器参数是环境变量覆盖,因为它们会改变数字的含义:`BULK_BYTES`(默认
200 000;当 CPU 计数器 100 Hz 的分辨率重要时,把它提到一秒以上的流量)、
`SMALL_REQUESTS` 与 `SMALL_BYTES`(默认 2000 × 64 B)、`CLAIM_MODE`(不设置,即测量
产品自身的默认值;`multiplex` 选另一种数据通道模式)。

## bench 模型(测量标准)

关于一次改动的每一项性能 claim,都用同一个模型做出:`benches/scripts/bench/`。它不是上面
的 sweep,两者不共享任何数字。sweep 回答的是*一个工具在路径劣化时、与它的对端相比表现
如何*,每个阶段一个样本;本模型回答的是*这次改动付出了什么代价,以及这个差异是否大于本轮
运行自身的分辨能力*,在反复多轮中进行,且每一轮都带一个对照。来自一方的数字不能与来自
另一方的数字相比较。

过去与 sweep 并排存在的那些按问题分设的仪器——L3 与 L4 各臂的比较 runner、一个内存采样器、
一个 HTTP 延迟脚本——现在要么是本模型的场景,要么已经消失:不在下面那张注册表里的数字,
没有可供比较的定义。

```bash
sudo -n just bench                     # the smoke profile, about a minute
sudo -n just bench --profile dev --aa  # the default loop for an optimization
sudo -n just bench-doctor              # what this host can and cannot measure
just bench-report ~/tmp/bench-*.json   # a stored run: tables, floors, verdicts
just bench-compare a.json b.json       # A/B two runs, or refuse to
just bench-selfcheck                   # the model's own checks (a fast gate)
```

### 模型强制的规则

- **一个指标只在代码里定义一次。** 单位、方向、它作为比值时所用的分母、能够产出它的工作
  负载种类,以及值得称为一个 claim 的最小差异,全都写在 `model.METRICS` 里;下面那张表
  就是从这个注册表生成的,`just bench-list` 会把它打印出来。一个指标若描述成一种算法、
  计算的却是另一种,`just bench-selfcheck` 会失败。
- **对照臂是强制的。** 每个场景还会在同一条拓扑、同一组端口与同一个后端上再跑一遍,路径
  上没有工具。没有它,慢探针和慢隧道就是同一个读数,所以本模型总是把一个工具臂*对着它
  自己的对照*上报,而不是单独上报。
- **每个臂共用一条拓扑。** 三个 network namespace、两对 veth 与两个 TUN 设备;L4、L3 与
  对照各臂只在访客拨向的地址、以及写进各自配置的模式上不同,再无其它——同一个二进制、
  同一个后端、同一组端口、同一个探针、运行中的同一个阶段。正是这一点才让一个 L3 数字与
  一个 L4 数字可比。它的代价是 root,而 `just bench-doctor` 会在一轮运行不得不自己去
  发现之前,就把这一点说明白。
- **一轮运行在取第一个样本之前,就陈述它的整套方法。** 结果文件带一个指纹,覆盖拓扑、
  各个场景及其*解析后*的参数、各仪器的节奏与本模型自身的代码。只有指纹一致时,两份文件
  才可以比较,而 `just bench-compare` 会逐一列出每一个有差异的键,而不是印出两种方法之间
  的一个差值。
- **本轮运行测量它自己的分辨率。** 有一个臂会在两个名字下各测一次(`--aa`;在 `dev` 与
  `full` 里默认开启),这两半之间的差异——逐轮配对,于是主机的漂移被抵消——就是本轮运行
  能够相信的最小差异。每个判定都会把该指标自身的显著性下限抬到那个数字,而本轮运行会把
  各道下限印在表格旁边。16% 的分辨率是对本轮运行的一句陈述,不是一个借口:它指出该改
  什么(更长的工作负载、更多轮次)才能分辨得更细。
- **一个判定有五种状态,而"没有 claim"是其中之一。** `claim` 要求每一个配对轮次在符号上
  一致*且*两道下限都被越过;`directional` 是一个方向,但路上有分歧或有一道下限挡着;
  `indistinguishable` 落在本轮运行自身的离散度之内;`single-round` 拒绝从一次测量里读出
  一个方向;`unavailable` 指明什么没有被测量。任何臂都产不出的指标,会带着仪器给出的原因
  上报,绝不报成零。
- **证据跟着数字走。** 每个格子都记录它跑过的命令、它读过的计数器(每个接口的字节数、
  包数与丢弃数;每个 daemon 的 CPU 秒数与 `/proc/<pid>/io`;各 namespace 的 TCP MIB;
  峰值 socket 数)、逐轮的原始样本数组,以及它的探针留下的日志。结果文件随运行边跑边写,
  所以一场被打断的战役仍然可以分析。
- **结果住在仓库之外。** 一轮运行写 `~/tmp/bench-<stamp>.json`,产物就在它旁边(发起运行
  的用户的家目录,即便在 `sudo` 之下也是如此);`--out`/`--work` 可以把它们搬走,而一个
  已存在的 `--out` 会被拒绝,除非给出 `--force`。结果文件是某个决策的证据,不是仓库产物
  ——上面发布用的 sweep 才拥有那些被提交的数字。

### 指标

由 `model.METRICS` 生成;`just bench-list` 打印的是同一份注册表,而报告和判定渲染出来的
就是这些定义。

| 指标 | 单位 | 方向 | 是什么 | 除以 |
|---|---|---|---|---|
| `throughput_gbps` | Gbit/s | 越高越好 | 接收端窗口内的有效载荷字节数 × 8 / 测量窗口 | 工作负载的测量窗口 |
| `offered_gbps` | Gbit/s | 背景,不是判定 | 访客链路出方向字节数 × 8 / 测量窗口 | 工作负载的测量窗口 |
| `rate_per_s` | 1/s | 越高越好 | 完成的请求/响应对数 / 测量窗口 | 工作负载的测量窗口 |
| `rtt_p50_ms` | ms | 越低越好 | 探针逐次请求往返时间的 nearest-rank 中位数 | 一个请求/响应对 |
| `rtt_p99_ms` | ms | 越低越好 | 探针往返时间的 nearest-rank 第 99 百分位数 | 一个请求/响应对 |
| `rtt_max_ms` | ms | 越低越好 | 探针观测到的最差单次往返时间 | 一个请求/响应对 |
| `rtt_samples` | count | 背景,不是判定 | 取百分位数所依据的往返次数 | 无(样本数) |
| `udp_recv_mbit` | Mbit/s | 越高越好 | 探针收到的数据报数 × 载荷 / 探针自己的测量窗口(对一次 blast 来说,该窗口包含 drain) | 探针的接收窗口 |
| `udp_loss_pct` | % | 越低越好 | (发出的数据报 - 收到的数据报) / 发出的数据报 | 探针发出的数据报 |
| `udp_gap_p99_ms` | ms | 越低越好 | 探针收到的各次应答之间间隔的第 99 百分位数 | 一个收到的数据报 |
| `udp_rtt_p99_ms` | ms | 越低越好 | 探针数据报 echo 往返时间的第 99 百分位数 | 一个被 echo 的数据报 |
| `setup_p50_ms` | ms | 越低越好 | 建立一条连接所需时间的中位数,前提是工作负载每次请求都新开一条连接(访客为抵达而付出的建连代价) | 一条连接 |
| `cpu_s_per_gbit` | s/Gbit | 越低越好 | 工具 CPU 秒数(user+sys,两个 daemon 合计) / 访客报价的 Gbit | 访客链路出方向上的 Gbit |
| `cpu_cores` | cores | 越低越好 | 工具 CPU 秒数 / 测量窗口 | 工作负载的测量窗口 |
| `bytes_per_syscall` | B | 越高越好 | 工具进程的 rchar+wchar / syscr+syscw(I/O 粒度) | 一次 read/write 族系统调用 |
| `syscalls_per_s` | 1/s | 越低越好 | 工具进程的 syscr+syscw / 测量窗口 | 工作负载的测量窗口 |
| `wire_per_visitor_byte` | ratio | 越低越好 | 隧道链路字节数(双向) / 访客链路出方向字节数 | 访客报价的字节数 |
| `mean_carried_packet_b` | B | 背景,不是判定 | 隧道链路字节数 / 隧道链路包数,双向 | 隧道链路上的一个包 |
| `rss_peak_mib` | MiB | 越低越好 | 在工作负载进行中采样,工具各 daemon 的 RSS 峰值之和 | 一组进程 |
| `fds_peak` | count | 越低越好 | 工具各 daemon 打开的 fd 峰值之和 | 一组进程 |
| `threads_peak` | count | 越低越好 | 工具各 daemon 的线程数峰值之和 | 一组进程 |
| `service_sockets_peak` | count | 越低越好 | 服务端自己的 namespace 里,暴露服务端口上的 socket 峰值:该架构为每个访客保留的状态 | 一个访客 |
| `retrans_segments` | count | 越低越好 | 访客 namespace 与服务端 namespace 重传的 TCP 段数 | 一个 TCP 段 |
| `dropped_packets` | count | 越低越好 | 窗口内本拓扑各接口丢弃的包数 | 一个包 |

有两条约定这张表说不出来,因为它们属于工作负载:

- **速率的窗口是仪器自己的,而且它是有名字的。** bulk 速率取接收端预热之后的窗口
  (iperf3 的);往返速率取探针的测量窗口,而不是解释器启动的那一刻(启动成本记录在
  `meta.probe_startup_s` 里);数据报速率取探针的接收窗口,对一次 blast 来说它包含 drain。
  由计数器导出的比值(`cpu_s_per_gbit`、`wire_per_visitor_byte`、`syscalls_per_s`)用
  计数器的窗口,这个窗口恰好只框住工作负载的进程——所以一个比值的分子与分母覆盖的是
  同样的那几秒。
- **`wire_per_visitor_byte` 对单向流量有 1 的下限,对严格的请求/响应工作负载有 2 的
  下限**,因为它统计隧道链路的两个方向,而一次往返会在那里被搬运两次。要读它,就对着
  对照臂自己的读数读,绝不要对着 1 读。

### 场景

| 场景 | 工作负载 | 它支撑的 claim | 头号指标 |
|---|---|---|---|
| `bulk-1` | `bulk` | 一条 bulk TCP 流能承载多少,以及它每字节的代价 | `throughput_gbps` |
| `bulk-n` | `bulk` | N 条流是聚合起来,还是共享同一个上限 | `throughput_gbps` |
| `bulk-pair` | `bulk-pair` | 两个服务(或两条 L3 claim)是否各自承载一条完整的流,以此把每流上限与每主机上限分开 | `throughput_gbps` |
| `rr-1` | `rr` | 一条严格请求/响应流的往返速率与延迟 | `rtt_p99_ms` |
| `rr-16` | `rr` | 同上,但同时 16 条流:聚合速率与尾部延迟 | `rate_per_s` |
| `churn-16` | `rr` | 每次请求新开一条连接:访客付出的建连代价,以及该架构为每个访客保留的状态 | `rate_per_s` |
| `udp-pace` | `udp` | 一次限速的 UDP 会话:到达的比例是多少,间隔又如何 | `udp_loss_pct` |
| `udp-ladder` | `udp-ladder` | 在每一个报价速率上,UDP 路径从何处开始丢弃 | `udp_loss_pct` |
| `udp-blast` | `udp` | 探针以力所能及的最快速率报价时的数据报上限 | `udp_recv_mbit` |

| profile | 测量轮数 | 预算 | 用途 |
|---|---|---|---|
| `smoke` | 2(+1 预热) | 每个臂 ~45 s | 快循环:每一个头号指标,以秒计而不是以分钟计 |
| `dev` | 4(+1 预热) | 每个臂 ~150 s | 一次优化工作的默认档:每一个场景,以分钟计 |
| `full` | 6(+1 预热) | 每个臂 ~420 s | 发布级的 sweep:全部内容,需要多久就跑多久 |

### 怎么读一次结果

- **一个 profile 就是一种分辨率,而 smoke 的分辨率很宽。** 同一个未改动二进制在 `smoke`
  下反复运行(`--aa`),曾在往返格子上声称 13-20% 的差异、在最短的格子上声称 23-29% 的差异:
  在只有几秒长的臂上,模型自身的离散度就有这么大,而它会说出来,不会把它藏起来。请把
  smoke 的 claim 当作一个假设,用 `dev` 重新测——`dev` 存在的意义正是如此。
- **格子表是带范围的中位数**(`median (min to max)`),按臂在测量轮次上取。预热轮不计入;
  失败的轮次会被计数,并连同仪器的类型化原因一起列出,绝不混进平均值。
- **下限表就是本轮运行的分辨率**,按指标给出:A/A 差异、A/A 离散度、以及整轮运行中对照
  的漂移,再取三者中最大的那个,而一个 claim 必须越过它。产生最差读数的那个格子会被点名,
  因为那才是该多花时间的地方。
- **判定是按场景、按格子给出的**,每个工具臂对着对照给一份,再加上 A/A 孪生臂自己的判定
  ——孪生臂声称有差异的那个指标,就是本轮运行分辨不了的指标,而它会明说这一点。
- **一份结果文件就是 `meta`、`samples` 与 `summary`。** `meta` 承载方法(指纹、解析后的
  场景参数、拓扑、各仪器的节奏)、来源(修订、二进制的 sha256 与它自己那一行 `--version`、
  主机身份、两个校准探针)以及臂列表;`samples` 是每个臂、每一轮、每个场景、每个格子一条
  记录,各自带着它的指标、它类型化的缺失与它的证据;`summary` 是分析从这些样本里推导出来
  的东西——而 `just bench-report` 会重算它,因为样本才是证据,`summary` 只是对证据的一次
  渲染。
- **`just bench-compare` 按臂 id 比较两份文件**:同一个臂在两个构建里的对比读作"这次改动
  对这个臂做了什么",而对照臂自身的差值会先被印出来,作为两轮运行之间的漂移。如果指纹
  不同、主机身份不同,或者任一文件里的 CPU 探针或 loopback 探针缺失、或与对方不一致超出
  各自的容差(25% 与 15%;与下面的[可比性](#可比性)是同样的两个探针、同样的推理),比较
  就会被拒绝,并且每一条阻断理由都会被点名。一轮没有 A/A 孪生臂的运行,自身离散度是
  没有测量过的,所以只要参与比较的某一方缺了它,所有差异都只报成 `directional`,绝不报成
  claim:当结论要用来做决定时,两侧都要用 `--aa` 跑。

### 模型回答不了什么

- **来自另一台主机的数字。** 主机身份与两个校准探针随每一份文件一起走;在不同机器上的
  两轮运行会被拒绝,而同一台机器上、探针漂移超出容差的两轮运行也会被拒绝。
- **对照臂够不到的任何东西。** 没有任何无工具路径能跑的场景,按声明就是 `diagnostic`
  (场景目录会把它标出来),它产出的数字不带任何判定。
- **被整形路径下内核自己的行为**,以及工具的内部:本模型只整形自己拓扑的一条腿,并且只读
  外部可观测的状态,所以 `MOLEHILL_*` 计数器从不出现在比较里。下面那个 UDP 队列问题正因
  如此,才是一个 molehill 专有的*诊断*。
- **发布 sweep 的那些问题**——对端工具、脚本化的劣化时间线、数小时尺度上的漂移。它们
  仍然归 sweep 管。

## UDP 队列问题(不属于 soak 模型)

UDP 服务的数据报上限是**服务**的属性,不是阶段日程的属性,所以它有专门的仪器:
`benches/scripts/udp_stress.py` 启动真实的一对进程(`udp_workers` 可配),用**限速或
全速**的访客打它,并在每一步前后读取服务端的 `MOLEHILL_UDP_STATS` 行;最后一步是
对照——同样的访客**直接打 sink**。没有这个对照,慢 sink 和慢隧道从计数器上看是
一样的。同一主机、1400 字节数据报实测:单个访客从不丢包(它自己的 socket 缓冲把它
限在约 29.8k 数据报/秒),多访客把池打到约 1 Gbit/s 饱和,与 `udp_workers`(1/2/4 分别
1.14/1.00/0.98)和访客数都无关,扩散保持均匀,而丢弃量与该上限之上的超出部分相差
0.07% 以内。用户需要的数字在配置页 `udp_workers` 旁边。背后的探针是
`benches/scripts/udp_stress.py`;用同样的方式运行,就能在自己的主机上复现这个上限。

## 可比性

单个结果格子的读法——哪一侧说话、没有读数意味着什么、样本数——见
[怎么读一个格子](#怎么读一个格子)。

- **同模型、同方法、同主机。** 每份结果文件都记录方法版本、主机与 harness 修订;
  来自另一台主机或另一个模型的数字只是背景,不是基线。
- **gate 比较的是方法记录本身,不只是它的版本号。** 方法版本是整个模型的一个整数,
  所以它无法察觉底层换掉了阶段交接、drain 判据、重拨表或某个探针速率。
  `soak_check.METHOD_KEYS` 列出承载方法的那些键(日程、整形档、负载、SLO、探针速率
  与交接设置),比较会**被拒绝而不是被印出**,并列出有差异的键、以及某一方根本没有
  记录的键。缺失的键**不按默认值读**:它表示那份文件早于该仪器,替它编一个值等于编
  出一个方法。
- **同主机——同一个被测状态,走同一条路径。** 主机被记录为
  `hostname`(读者认得的那个名字)、`host_id`(machine-id 加 CPU 型号与核心数后
  哈希)以及**两个**每轮运行前测定、不含任何工具、且各自带着自身离散度的探针:
  `host_calibration` 测*状态*(SHA-256 过 192 MiB 缓冲,取三次中位数,单位 MiB/s),
  `host_loopback` 测快档真正骑的那条*路径*(512 MiB 过一次 loopback socket 对,
  取五次中位数,**在它自己的子进程里绑定到单个 CPU**,单位 Gbit/s——不绑定时,两个
  线程落在哪些核上决定了它们走哪条拷贝路径,探针会跨进程出现**双峰**:同一台空闲主机
  上 29.4-29.7 与 34.2-34.4 Gbit/s,这不是可比性键能承受的;而绑定必须放在子进程里,
  因为 `sched_setaffinity` 会被 runner 派生的一切继承,就地绑定会把整轮运行——工具、
  客户端与采样器——都锁在一个核上)。CPU 预算与 loopback 上限都是*机器*的属性,所以容器化
  bench 主机每次重启都换 hostname 不能破坏可比性——这正是 `host_id` 的用途。但身份
  键只是一个*名字*:在读不到 machine-id 的主机上它退化成 `cpu_model | nproc`,两台
  不同的机器因此可能哈希到同一个主机,而同一台机器在两轮之间也可能忙成另一台机器的
  样子。所以只有身份一致**且**两个探针都同意,两轮才可比:CPU 负载落在 25% 以内
  (`soak_check.HOST_CALIBRATION_TOLERANCE_PCT`),loopback 路径落在 15% 以内
  (`soak_check.HOST_LOOPBACK_TOLERANCE_PCT`——绑定后的探针跨进程重复性约 1.5%,
  四个忙循环下掉约 5%,而它要抓的效果是 25-39%)。两者并不重复——CPU 探针自身重复性
  约 2%,却对 loopback 上限**视而不见**:同一个 `host_id` 的两个容器实例之间,能摸到
  该上限的两个臂的 clean 格差了 25-39%,而 CPU 探针只差 1.7%——所以任何单独一个都
  不足以证明一次比较。早于某个探针的结果文件会针对那个探针被报成*无法核验*,而不是
  被读作一致;完全没有 `host_id` 的文件则退回比较记录下来的 hostname,朝安全的方向
  保守(拒绝比较)。
- **每一条阻断理由都会被报出来,而不只是第一条。** 一份基线可能同时不满足多项,
  只报第一条会让人以为清掉它这一对就能比较了。
- **重复出现的档位就是这一轮自己的重复实验。** 日程在每条时间轴首尾各测一次
  `clean`,那两个读数就是同一条件相隔约一小时的两个样本:`just soak-check` 会报出
  它们的离散度,而这就是每一个工具间差异必须超过的尺度。它只上报、从不判定——方差
  是数据,给它设阈值等于凭空发明一个。
- **逐项实测的数字来自一套退役的仪器。** v0.8.x 及更早的发布测的是每工具每网络条件
  一个平均值、进程每次冷启动,上报的是对重复取的中位数。那些表格不能与这些数字比
  较——每格冷启动的一个平均值看不到 wedge,而本模型的若干发现正是 wedge。下面那张
  逐项表里仍然依据它们的行已经标明,它们只作方向性参考:为你自己的场景重测一遍。
  历史数字留在各自版本的发布说明里。
- **方差是如实陈述的,不是抹平的。** 如果某个差异落在被比较各轮运行的离散范围
  之内,就按 directional 上报,不从中得出任何 claim。
- **阶段按出现次序比较,不按名字。** 日程以同一个 `clean` 条件开场也收尾,所以
  一轮运行的第 k 个 `clean` 与另一轮的第 k 个 `clean` 相比:返回阶段——恢复
  轴——是照着基线的*返回*阶段判的,不是照着它全新的时候。
- **tunnel pool 是弹性的,所以 pool 的尺寸是*结果*,不是设置。** 带共享弹性
  pool 的构建(`[client.data].shared_pool`、`[client.data].idle_timeout`、
  `[client.data.tcp|kcp].max_tunnels`)是**冷启动**的——没有访客需要之前不存在
  任何隧道——之后自行增长与收缩,上限是 `max_tunnels`。仍然带着旧的固定尺寸键的
  配置根本无法启动;请照
  [配置迁移对照表](configuration.zh.md#迁移到-010已移除的键)改写。下面逐项实测里
  的 `count` 数字就是在那个钉住尺寸的模型下测的,描述的是*钉住*某个 pool 尺寸的
  代价。它们是选择该上限的依据,不是对某一轮 pool 实际行为的预测——某一轮真实用
  到的尺寸由 `MOLEHILL_POOL_STATS` 时间线记录。

## 自己复现

在一台装有 `iperf3` 与 `tc` 的 Linux 主机上(见 `just bench-deps`):

```bash
just soak-peers    # 下载各对端工具的最新 release 二进制
just soak          # 一个工具(或一批)走一遍阶段日程
just soak-plot     # 渲染图表并打印 markdown 表格
just soak-check    # 判定:完整性、端点、SLO、漂移
```

发布扫描是一条命令——阶段日程与负载斜坡装进同一份产物(见
[release.md](release.md),"Benchmarks"):

```bash
just soak --test=rrul,capacity --tools molehill,frp,rathole,nps \
     --out benches/scripts/soak/results-soak-vX.Y.Z.json
```

`just soak --help` 会列出测试类型、各 variant(`mux`、`shared`、`direct`、
`mux-off`、`noise`、`noise-direct`、`mux1`、`mux8`、`kcp4`)、阶段日程与批处理
控制;负载、SLO 与采样
率这些旋钮都是环境变量(`SOAK_*`),每一个都会被回显进结果 meta。

要在不做完整一轮的前提下比较**你自己的两个构建**——或一个构建的两种配置:

```bash
just soak --test=screen --path=loss1 --streams-max=8 \
     --ab /path/to/bin-a,/path/to/bin-b --out results-screen.json
just soak --test=screen --path=clean --ab-variants mux,direct \
     --out results-screen-variants.json
just soak-check --screen results-screen.json
```

只有当每一步的符号一致且超过阈值时,判定才声称存在差异,其余一律称为
directional。它是有**作用域**的:只回答在该路径类别上是否值得沿这个方向推进,
从不回答这个改动能否发布——那由 sweep 与发布门禁决定。

发布门禁——一个公开的数字在被某个 tag 带上之前必须满足什么——见
[release.md](release.md)。
